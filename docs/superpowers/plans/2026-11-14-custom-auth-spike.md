# Custom auth: Clerk spike (PR 1)

Plan: `docs/superpowers/plans/2026-11-14-custom-auth.md`. This settles readiness gaps 4, 14 and 15 and proves the Clerk behaviour every later PR leans on. It ships **no production code**: the probe page is throwaway and is never committed. The PR is this document.

Instance: Concert Crawl development instance, named in the results by its publishable key's `pk_test` prefix only. Settings at the time (set 2026-11-14 to match The 99, plus Hugh's calls): Strict enumeration, lockout 10 tries / 60 min, zxcvbn >= 2, HIBP including on sign-in, Client Trust on, legal acceptance on (`/legal/terms`, `/legal/privacy`), email-code verification, Smart CAPTCHA on, Google with subaddress block and account picker.

## Static findings (no stack needed)

Read from The 99's working implementation (`f45838816`, `@clerk/nextjs` 7.10.0) and from the installed Clerk types (`@clerk/nextjs` 7.9.25, `@clerk/shared` 4.44.1).

1. **The Future signal API is the one to use.** `useSignIn()`, `useSignUp()` and `useClerk()`; no `isLoaded` or `setActive`. Every call returns `{ error }` rather than throwing (wrap the network throw anyway). A session is activated with `signIn.finalize({ navigate })` or `signUp.finalize({ navigate })`; a pending session task needs a full load to `/sign-in/tasks/<key>`, so that path must be public in `proxy.ts`.
2. **Sign-in call sequence** (proven in production at The 99): `signIn.password({ identifier, password })`; `signIn.emailCode.sendCode` then `verifyCode`; reset with `signIn.create({ identifier })`, `resetPasswordEmailCode.sendCode`, `verifyCode`, `submitPassword`; then dispatch on `signIn.status`: `complete` finalizes, `needs_second_factor` and `needs_client_trust` both go through `signIn.mfa.sendEmailCode` then `mfa.verifyEmailCode`, `needs_new_password` is the breached state.
3. **Error codes.** Wrong credentials: `form_password_incorrect`, `form_password_or_identifier_incorrect`, `form_identifier_not_found`, `user_locked`, `strategy_for_user_invalid`: all one "didn't work" line, so a locked account reads like an unknown one (this answers the leak half of gap 4). Breached: `form_password_pwned` (and the `__sign_in`, `compromised` and `untrusted` variants), read first because it can arrive with the weak code. `form_password_not_strong_enough` and `form_password_length_too_short` have their own lines. A 429 and `captcha_*` are deliberately unmapped and fall to the generic "try again" line, never to a refusal.
4. **Timing pads** (900 ms, 1500 ms for reset) pad only fast answers; send errors are swallowed so "code sent" always shows. The pad hides a gap shorter than the floor; Strict covers the rest.
5. **The OAuth transfer** is refused in code. A custom `sso-callback` that does not render `<HandleSSOCallback/>`: wait for `clerk.loaded`, resolve the pending bot challenge with `clerk.__internal_resolvePendingProtectCheck(flow)` (fail closed, and report if the function is missing or throws), then branch on `signIn.status` (`complete` finalizes, a second-factor status goes to the code screen, everything else, including a Google account with no account, goes to `/sign-in?google=refused`). It never transfers a sign-in to a sign-up. The installed types declare `__internal_resolvePendingProtectCheck`, so a unit test must fail if a Clerk bump drops it.
6. **The installed types carry what the plan needs:** `legalAccepted` on the sign-up password and sso calls (`signUp.d.ts:83`) and as a sign-up field error, the `needs_client_trust` and `needs_protect_check` sign-in statuses, and `__internal_resolvePendingProtectCheck`.
7. **Gotchas from The 99's comments** that apply here: `signUp.password()` starts a fresh sign-up (relevant only to its invitation ticket); the Future `signUp.update` type omits `password` though the API accepts it; Clerk's sign-up changes across awaits, so re-read `signUp.status` each time; read `signIn` only after `clerk.loaded` on a reload; bfcache restore re-shows a busy Google button, so clear it on `pageshow` with `persisted`.
8. **Pin the Clerk scripts** (`CLERK_JS_VERSION`, `CLERK_UI_VERSION`): the major-tag URLs answer two uncacheable 307s, about 560 ms on a slow phone. Re-prove the Google sign-up path by hand on each bump.

## What The 99 does not cover, and this spike must prove for CC

The 99's sign-up is invitation-ticket only. CC's sign-up is email, password and an emailed code, with legal acceptance and Smart CAPTCHA.
