# #794 — Logged-out app UX — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Take [#794](https://github.com/HartiganHM/concert-crawl/issues/794) — logged-out app UX: navigation, header, browse-only shape — from a 🟢 Green design handoff into shipped code. A visitor with no session gets the **whole read-only app**: the calendar, event detail, venues, search, and a teaching `/watching` page, inside the **same shell** signed-in users see, with gated affordances that look identical at rest and tell the truth in their accessible name.

**Architecture:** The change is mostly a **reach** change, not a rendering change. `apps/web/src/app/(protected)/(main)/*` server components are already token-optional (`events/page.tsx`, `venues/page.tsx`, `venues/[slug]/page.tsx`, `events/[id]/page.tsx` all branch `token ? apiClient : publicApiClient`). Three things stand between them and an anonymous visitor:

1. `apps/web/src/middleware.ts:60` — `auth.protect()` catches everything not in `isAlwaysPublic`.
2. `REQUIRE_BETA_AUTH` — one env flag mounting router-level auth on four Hono routers.
3. `apps/web/src/app/(protected)/layout.tsx` — makes **no `auth()` call**, so its five mounted gates begin rendering for anonymous visitors the moment the matcher broadens.

So the build order is: land the copy fix and the surfaces that are already public, add the gates, open the API, build the signed-out surfaces while they are still unreachable, and **flip the matcher last** as a small, heavily-tested keystone PR.

**Tech Stack:** Next.js 15 (App Router), React 19, TypeScript strict, Clerk (edge `clerkMiddleware` + `useAuth()` client), Hono + Zod, Drizzle, TanStack Query, Vitest, Playwright.

**Spec:** [`docs/superpowers/specs/2026-07-25-794-logged-out-ux-design-brief.md`](../specs/2026-07-25-794-logged-out-ux-design-brief.md) (merged in PR [#1198](https://github.com/HartiganHM/concert-crawl/pull/1198))
**Design handoff:** `design/design_handoff_logged_out_ux/` — Readiness verdict: 🟢 **Green** (R1 🟡 → R2 🟢, audited 2026-07-27, `READINESS.md`). 15 decisions in `DECISIONS.md`; measurements + verbatim copy in `SPEC.md`; the task-off artifact is `LO_INVENTORY` in `lo-inventory.jsx` (7 groups, 48 rows).

## Global Constraints

- **TDD.** Every new module lands with tests first. Every task below names the test that proves it.
- **Vocabulary is LOCKED** (`CLAUDE.md` → Customer-facing vocabulary). **Watching** — never "Saved", "Favorites", "Following". **Submitted prices**. **Price check**. There is no "Saved" concept in this product. PR-A exists because three shipped strings violate this today.
- **The Watching affordance is an EYE** (lucide `Eye`, already shipped in `WatchShowButton.tsx`). There is no heart in this product and never has been. Do not write the word "heart" into any file in this build; grep the diff for it before every push.
- **All customer-facing strings in `definitions/copy.ts`** — project convention. Copy lifts **verbatim** from `design/design_handoff_logged_out_ux/SPEC.md` and the drop's `.jsx` `*_COPY` maps. Do not rewrite it; the READINESS audit locked it, and R2 specifically swept "Saved while you were signing up" → "Kept while you were signing up" across four files.
- **Tokens only.** Every color reads `var(--*)`. No ad-hoc hex on authored surfaces, no Tailwind `dark:` variants. Nine production themes come off one token set; parity holds across all nine. The only legitimate literals are theme-preview swatches (a preview of *other* themes' tokens) and the `IA_PALETTES` identity artwork, which is theme-independent by design.
- **TypeScript strict; no `as` casts.** Zod `safeParse` at boundaries (the `intent` query param in PR-G, `localStorage` reads), type guards for union narrowing, declaration merging for library types. Note `apps/web/src/components/auth/OnboardingThemeFlush.tsx:28` already carries an `as ThemeName` — PR-C touches that file and should replace it with a Zod parse in the same commit.
- **Components:** arrow functions, no `handle*` names, logic in `lib/`, semantic HTML, no native `title=` tooltips on authored surfaces.
- **Mobile/desktop parity in the same PR — non-negotiable.** Every consumer surface here has both breakpoints in the handoff (`SPEC.md` §2 header at 320/mobile/desktop, §3 popover vs bottom sheet, §7 `OnboardingShell` mobile + `OnboardingDesktop`). A PR that ships one breakpoint is incomplete.
- **A11y floor, same PR.** 44px minimum hit areas (the 26px bottom-nav disc gets a 56×44 target), visible `--focus` ring at 2px offset 2, keyboard reachable in DOM order, honest accessible names on identical-looking gated affordances, auth-seam state changes announced **once**.
- **Gated affordances render identical pixels at rest** (§3.10, locked). No lock glyph, no dimming, no disabled state, no skeleton, nothing that reads "incomplete" (DECISIONS #1). Honesty lives entirely in the `aria-label`, plus `aria-haspopup="dialog"` + `aria-expanded`, and **`aria-pressed` is omitted entirely** when signed out — not shipped as `aria-pressed="false"`. The eye is not a toggle without a session, so it must not report a pressed state.

- [ ] **Step 1: Resolve the click conflict — read this before writing code**

The stage today is a `<div role="button" tabIndex={0} aria-label="Next poster" onClick={advance} onKeyDown={…}>` wrapping four absolutely-positioned poster layers (`LandingPosterAnimation.tsx`, `LPStack`). DECISIONS #7 says **the whole card is one link**. A link nested inside a `role="button"` that advances the stack is both an a11y violation (nested interactive content) and ambiguous behavior.

**Resolution:** the stage stops being interactive. Remove `role="button"`, `tabIndex`, `onClick`, and `onKeyDown` from the stage element and drop its `aria-label`. Advance-on-tap is replaced by:

- the **top layer only** becomes the `<Link>` (the three behind it get `aria-hidden="true"` + `tabIndex={-1}` + `pointer-events: none`, which they need anyway — they are decorative depth, and without this the tab order picks up four hidden posters);
- the existing **dot pager** keeps manual advance, and its `ev.stopPropagation()` calls become unnecessary once the stage is inert (remove them);
- the autoplay `intervalMs` timer is unchanged.

This is the one place where the plan makes a call the handoff did not: the handoff says "the poster itself and its stack animation are the shipped ones — #794 adds only link chrome," but the shipped stage's tap handler cannot coexist with a link. Making the top layer the link and leaving the pager as the manual control preserves every user-facing behavior except tap-to-advance, which the pager already provides.

- [ ] **Step 1: Understand why "renders nothing" is not enough**

Both components already render nothing without a session — but both **mount and hold auth-dependent effects**. `FirstWatchNudgeGate` subscribes to `queryClient.getMutationCache()` in a `useEffect` and only checks `if (hidden) return null` at line 93, *after* the effect. `OnboardingThemeFlush`'s effect reads `localStorage` and calls `getToken()` then `patchMe()`. Anonymous visitors would be running a mutation-cache subscription and an unauthenticated `patchMe` attempt on every page.

React forbids conditional hooks, so the fix is **not** an early return above the `useEffect` — it is a guard **inside** the effect body plus a `null` render:

```tsx
// FirstWatchNudgeGate.tsx
const { isSignedIn, isLoaded, getToken } = useAuth()
```

## Phase / PR-D — Retire `REQUIRE_BETA_AUTH`

One env flag mounts router-level auth on four Hono routers with **two different bars**. The handoff's open question #3 is blunt about the stakes: *"Design assumes public reads. If the flag stays on for any of the four routers at launch, half of this drop is unreachable."*

### The disposition, decided

**Delete the flag and all four router-level guards. Do not make it per-router, do not flip it to `false` and leave the code.**

The justification is that **every mutating route on those four routers already carries its own auth**, verified by reading each one:

| Router | Route | Own guard | Verdict |
|---|---|---|---|
| `events.ts:126` | `GET /` | `clerkMiddleware()` optional-auth | read — public |
| `events.ts:501` | `GET /genres` | none | read — public |
| `events.ts:513` | `GET /availability` | none | read — public |
| `events.ts:568` | `GET /:id` | `clerkMiddleware()` optional-auth | read — public |
| `events.ts:1129` | `GET /:id/related` | none | read — public |
| `events.ts:1216` | `POST /:id/watch` | `clerkMiddleware()` + explicit `if (!authInfo?.userId) → 401` (line 1217–1219) | **self-guarded** |
| `events.ts:1264` | `DELETE /:id/watch` | `clerkMiddleware()` + explicit `if (!authInfo?.userId) → 401` (line 1265–1267) | **self-guarded** |
| `search.ts:15` | `GET /popular` | none — and the shipped comment already says *"no auth required"* | read — public |
| `venues-public.ts:33` | `GET /` | none | read — public |

Verify with a grep before deciding.

- [ ] **Step 1: Answer the handoff's open question #1 — decide client-side replay**

The question: *"Does `intent=watch:{id}` get replayed server-side on first authenticated request, or client-side after hydration? The confirmation strip assumes the eye is already filled on first paint."*

**Decision: replay client-side, immediately on mount at the destination, with an optimistic cache seed so the eye paints filled.**

Server-side replay is the tempting answer because it satisfies "filled on first paint" literally, but it means a `GET` request performing a **write** — the destination is `/events/[id]`, reached by navigation, and a page render that mutates watch state is replayed by any refresh, prefetch, or bot. There is no idempotency key available at that point and the route is `force-dynamic`, so Next.js will happily re-render it.

Client-side replay keeps the write in a `POST` where it belongs. "Filled on first paint" is preserved by seeding the React Query cache optimistically before the mutation resolves — the same `useWatchToggle` optimistic path the app already uses for a normal tap. If the mutation fails, the optimistic seed rolls back and **no confirmation strip renders** — which is exactly the designed failure behavior (below).

```ts
    expect(decodeIntent(bad)).toBeNull()
  }
})
```

The intent arrives from a URL a visitor can edit. It is a system boundary, so it is `safeParse` — **no `as` casts**, and an unrecognized action decodes to `null`, not to a default.

- [ ] **Step 1: The exact new form**

Current state, verbatim (`middleware.ts:5-16`):

```ts

  '/', '/auth/code(.*)', '/sign-in(.*)', '/api/webhooks(.*)',
  '/api/pwa/icon(.*)', '/legal(.*)',
```

New form:

```ts
/**
 * Routes any visitor may reach, signed in or out.
 *
 * ⚠️ Adding a pattern here removes ALL auth from every path underneath it.
 * `/me` and `/admin` must never be reachable from this list, directly or as a
 * prefix. Every addition needs a negative case in middleware.test.ts proving
 * the private neighbours still redirect. See #794.
 */
const isAlwaysPublic = createRouteMatcher([
  '/',
  '/auth/code(.*)',
  '/sign-in(.*)',
  '/api/webhooks(.*)',
  '/api/pwa/icon(.*)',
  '/legal(.*)',
  // #794 — browse-only shape. Payload gating for these lives in the page
  // components and in apps/api, not here.
  '/events(.*)',
  '/venues(.*)',
  '/search(.*)',
  '/watching(.*)',
  '/onboarding(.*)',
])

/** Sign-up still requires an invite code during private beta. */
const isInviteGated = createRouteMatcher(['/sign-up(.*)'])

/** Signed-in users get bounced off these back to /events. */
```

Three changes, each deliberate:

1. **Four browse routes added.** `/watching` is public *as a route* and gated *as a payload* — the page renders `<WatchingSignedOut />` (PR-F Task 15). Middleware is the wrong layer for that distinction; a redirect there would make the tab dead on the signed-out bottom nav, which is exactly the shape §3.4 rejects.
2. **`/onboarding` moves from `isInviteGated` into `isAlwaysPublic`, and leaves `isPreAuth`.** PR-G made it a permanent post-auth route reachable from the account menu. Leaving it in `isPreAuth` would redirect a signed-in user opening the tour straight back to `/events` — the menu row would appear to do nothing. Leaving it in `isInviteGated` would bounce a signed-in user without the cookie to `/auth/code`.
3. **`/sign-up` keeps its invite gate.** Beta-artifact retirement (lifting `invite_verified`, `/auth/code`, `BetaPill`) is out of scope. Browse opens; signing up does not.

**Not added, and why each stays private:**

| Path | Stays private because |
| --- | --- |
| `/me` | Account, watch history, submitted prices, theme, billing. Note `/me` is *not* a prefix of any pattern above. |
| `/admin(.*)` | Admin surface. It has its own role check downstream, but must never depend on that alone. |
| `/api/*` (except the two listed) | Route handlers with no independent auth. |
| `/changelog` | Signed-in-only today; §3 doesn't ask for it. Not in scope. |
| `/artists/(.*)` | **Route does not exist.** See Task 23. |

- [ ] **Step 2: `unauthenticatedUrl` — `/` becomes `/sign-in`**

`middleware.ts:34` currently ends the handler with:

```ts
await auth.protect({ unauthenticatedUrl: new URL('/', req.url).toString() })
```

Sending an unauthenticated visitor to the marketing page was right when *everything* was private — the landing page was the only thing they could see. After this PR, a signed-out visitor browsing `/events` who lands on `/me` gets silently thrown to marketing with no explanation and their place lost. §3.12 requires they arrive at sign-in and come back:

```ts
const signInUrl = new URL('/sign-in', req.url)
signInUrl.searchParams.set('redirect_url', req.nextUrl.pathname + req.nextUrl.search)
await auth.protect({ unauthenticatedUrl: signInUrl.toString() })
```

Use `pathname + search` — never `req.url` — so an absolute origin can't be smuggled into `redirect_url`. Clerk validates `redirect_url` against its allowed origins, but building it from a relative pathname means we don't depend on that.

- [ ] **Step 3: Leave `config.matcher` alone**

`middleware.ts:60-68` is the Next.js-level matcher (which requests invoke middleware at all), not the auth decision. It is unrelated to this change and editing it risks skipping middleware entirely on a private route. Do not touch it.

## Self-Review notes

Three places this plan **overrides or resolves** an input rather than following it. Each is deliberate; a reviewer should check these first.

1. **The landing poster stack (PR-B Task 4).** `DECISIONS.md` #7 says the whole card is one link. The shipped `LPStack` stage is a `role="button"` that advances the carousel (`LandingPosterAnimation.tsx`), and four absolutely-positioned layers means a naive "wrap it in a link" produces four overlapping links. Resolution: the stage becomes inert, the **top layer only** is the `<Link>`, the three behind it are `aria-hidden` + `tabIndex={-1}` + `pointer-events: none`, and the dot pager stays the manual control. This is the one place the plan overrides the handoff.

2. **Bottom-nav slot 4 (PR-E).** The inventory describes it as opening the account menu in both states. The code links to `/me` in both states. The plan changes the signed-out branch only, because removing shipped signed-in behaviour needs explicit approval.

3. **`MobileProfileEntry` is dead code.** Repo-wide grep finds the export and one log string in `consumer/definitions/copy.ts:613` — no mount site. PR-E must **mount** it, not merely modify it. Any estimate that treated this as an edit is low.

Two judgement calls worth a second opinion:

- **`REQUIRE_BETA_AUTH` is deleted, not flipped (PR-D).** Reading every route on all four routers shows each mutating route self-guards (`events.ts:1216`, `:1264`; `price-submissions.ts:228`, `:538`), so removing the flag opens **reads only**. Keeping the flag as a permanently-`false` env var is a trap that would eventually get flipped back on. It goes.
- **Intent replay is client-side (PR-G Task 19),** answering handoff open question #1. Server-side replay would make a GET perform a write on a `force-dynamic` route with no idempotency key — a refresh or a prefetch would re-fire it. Client-side replay plus optimistic cache seeding keeps the write on a real user action.

**The riskiest task in the plan is PR-H Task 20.** Five added strings in one matcher decide whether `/me` and `/admin` are public. Task 21's negative cases exist for exactly that reason, and the mocked matcher is deliberately *looser* than production so those tests fail more readily than reality does.
