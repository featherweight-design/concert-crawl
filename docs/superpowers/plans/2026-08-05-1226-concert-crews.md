# Concert Crews — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship [#1226](https://github.com/HartiganHM/concert-crawl/issues/1226) — a crew is **a lens on your people**, not a per-event roll-call. Two surfaces: a **Browse lens** that filters the calendar to shows one of your people is going to, and a **Crews destination** that holds the roster, what's coming up, and what you went to together.

**Architecture:** Four net-new tables (`crews`, `crew_members`, `crew_invites`, `crew_mutes`). **No new attendance signal** — crew presence is derived at read time by joining `crew_members` against the shipped `user_events.attending_at` (`packages/db/src/schema/social.ts:60`). One new Hono router (`/v1/crews`) plus a deliberately public invite-resolution router. One new entitlement key (`crews`) gating **creation only**. Three new bell-only notification categories. Crews becomes the **fifth** bottom-nav slot.

**Tech Stack:** Next.js (App Router), React, TypeScript strict, Tailwind, Drizzle/Postgres, Hono, Zod, Vitest, Playwright.

**Design handoff:** `design/design_handoff_concert_crews/` — readiness verdict **🟢 Green** (`READINESS.md`, merged in PR [#1456](https://github.com/HartiganHM/concert-crawl/pull/1456) after five rounds: R1 🟠 → R2 🟡 → R3 🟡 → R4 🟡 → R5 🟢).
**Design brief:** `docs/superpowers/specs/2026-08-02-1226-concert-crews-design.md` (PR [#1371](https://github.com/HartiganHM/concert-crawl/pull/1371)).

## Decisions this plan makes (they were open; they are not any more)

Recorded here so implementers conform rather than re-deciding. Each has its reasoning attached.

### D1 — There is no `crew_shows` table. Crew shows are a query.

The design extraction floated denormalizing crew attendance into a fifth table for render speed. **Rejected.** `user_events` already has exactly the index this query wants:

```ts
// packages/db/src/schema/social.ts:71-73
userAttendingIdx: index('user_events_user_attending_idx')
  .on(table.userId, table.attendingAt)
  .where(sql`${table.attendingAt} IS NOT NULL`),
```

A crew is capped at 12 members, so the widest possible crew-shows query is a 12-way `userId IN (...)` against a partial index — this is not a scale problem, and a denormalized copy would need invalidating on every attendance toggle, every join, and every leave. Exhaust existing fields before adding columns. Net-new tables stay at **four**.

### D2 — `crews.id` is a uuid the client may supply.

The handoff asks for a client-minted id so the create-sheet patch preview is truthful (the patch is seeded from the id, so a server-minted id would make the preview a lie). The house pattern is `uuid('id').primaryKey().defaultRandom()`. Both are satisfiable at once: keep `defaultRandom()` as the column default, and let `POST /v1/crews` accept an optional `id: z.string().uuid()`.

This is safe because the id is **not a capability** — the invite token is. Knowing a crew id grants nothing. It also makes create idempotent: a retried POST with the same id hits the primary-key conflict and returns **409** instead of minting a duplicate crew.

### D3 — Invite tokens are stored in plaintext, and that is forced by the design.

Two token patterns already ship: HMAC (`apps/api/src/lib/email-unsubscribe.ts:38-72`, unrevokable by construction) and DB-backed random (`apps/api/src/routes/admin/invite-codes.ts:13-17`, plaintext at rest). Crews need expiry **and** revocation, so HMAC is out.

Hashing the token at rest is the reflexively safer choice and it **cannot be done here**: the invite sheet must re-display the live link to any member at any time (`crew-invite.jsx`, "Link box: monospace URL, copy button"). A hash is one-way, so re-display requires the plaintext. This matches the `invite_codes` precedent, where the value is a shareable token rather than a secret like a password.

Mitigations that *are* in scope: 72 bits of entropy (`randomBytes(9).toString('base64url')`), a hard 7-day expiry, revocation, and a `crew_invites` row that grants membership in exactly one crew and nothing else. One more that costs nothing: because the token *is* the capability, it must never reach a log line, a Sentry breadcrumb, or a structured error body — including on the 404 and 409 paths, where the temptation to echo the offending parameter is highest. Log the resolved `crewId`, never the token.

### D4 — The 12-member cap is enforced under a row lock.

`SELECT ... FOR UPDATE` on the `crews` row inside the join transaction. Without it, twelve people tapping a forwarded link at once all read `memberCount = 11` and all insert. A unique index cannot express "at most 12 rows in this group", so the lock is the mechanism.

### D5 — Mute suppresses at **write** time, not read time.

A muted crew writes no notification rows at all. Cheaper than filtering on read, and it gives the right semantics: unmuting surfaces what happens *next*, not a backlog of what you deliberately silenced.

### D6 — Lapse handling requires no lapse-handling code.

Because `requireFeature('crews')` gates **only** `POST /v1/crews`, a creator whose subscription lapses keeps every crew they already made, keeps the lens, keeps the roster, and loses only the ability to start another one. Brief §3.12 ("Premium buys the act of creating a crew, not the crew's continued existence") falls out of the gate placement. **Do not add a lapse branch anywhere.**

## ✅ Resolved — `/crew/join/<token>` and the beta invite wall

Both questions were settled with Hugh on 2026-08-05, after tracing the funnel. Recorded here so PR-3 does not reopen them.

**(a) Neither public list. The route stays authenticated.**

The original framing was a false binary. `/crew/join/<token>` goes in *neither* `isAlwaysPublic` nor `isPublicOnceLaunched`, so it falls through to the final `auth.protect()` block (`middleware.ts:204-213`). That block already builds a `redirect_url` from `toSafeReturnPath(pathname, search)` and hands it to Clerk, so a signed-out **but registered** beta member tapping a crew link signs in and lands back on the join page. That is the "invite friends already in the beta" case, and it needs no new code and no #794 exposure — nothing about a crew is readable without an account.

Public-ness only ever mattered for visitors with no account at all, which is not the audience during beta.

**(b) Point a not-yet-onboarded friend at `/auth/code`, and carry the return path.**

Chosen over (b1) "a crew token also satisfies the beta gate", which would have let any crew member mint beta access. The visitor completes the normal beta funnel and is returned to the crew link at the end — the link doubles as a nudge for friends sitting on an unaccepted beta invite.

This needs real plumbing, because **the return path is dropped at three hardcoded terminals**:

| Hop | Behaviour today | Evidence |
|---|---|---|
| middleware → `/auth/code` | Redirects to a bare `new URL('/auth/code', req.url)`; no `redirect_url` attached | `middleware.ts:194-199` |
| `/auth/code` → `/onboarding` | Server action ends in a bare `redirect('/onboarding')` after setting the signed `invite_verified` cookie | `apps/web/src/app/auth/code/actions.ts:64` |
| `/sign-up` → `/auth/complete` → `/events` | `forceRedirectUrl="/auth/complete"` is hardcoded, and `/auth/complete` ends in a bare `redirect('/events')` | `sign-up/[[...sign-up]]/page.tsx:11`, `auth/complete/page.tsx:54` |

A query param cannot survive that middle stretch, because Clerk's own screens sit between `/auth/code` and `/auth/complete` and `forceRedirectUrl` is fixed. **A cookie is the carrier**, and the funnel already sets one in exactly the right place: `/auth/code`'s server action writes a signed `invite_verified` cookie using `INVITE_COOKIE_SECRET`. The return path rides alongside it, using the same signing helper, and `/auth/complete` consumes and clears it in place of the hardcoded `/events`.

Sanitising is already solved and must be reused rather than rewritten: `sanitizeReturnPath` in `apps/web/src/lib/auth/intent.ts:74` rejects anything that is not a plain in-app absolute path (`//evil.com` and `/\evil.com` both fail its second-character check).

Do **not** route this through the `intent` mechanism in that same file. `Intent` is `action:eventId` with a UUID guard, it travels as a visible query param through Clerk's screens, and the crew token is a capability — putting it in an `intent` string would widen the token's exposure for no gain. The return path is the URL the visitor is already on; the token gets no new surface.

## Phase / PR-1 — Data model, entitlement key, notification categories

### Task 1: Schema module `packages/db/src/schema/crews.ts`

- [ ] Four tables, house patterns throughout (`uuid().primaryKey().defaultRandom()`, `text('user_id')` for Clerk ids, `timestamp({ withTimezone: true })`).

```ts
export const crews = pgTable('crews', {
  id: uuid('id').primaryKey().defaultRandom(),
  name: text('name').notNull(),
  // Clerk user id of the current keeper. Moves on handoff, so this is
  // deliberately NOT named createdBy — who created the crew is not a fact the
  // product uses. Only this user may rename, reroll, remove members, or delete.
  keeperId: text('keeper_id').notNull(),
  // Seed input for the patch alongside crews.id. Written ONLY by an explicit,
  // confirmed "New patch" action. Never by rename, never by membership change.
  patchSalt: integer('patch_salt').notNull().default(0),
  createdAt: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
  updatedAt: timestamp('updated_at', { withTimezone: true }).notNull().defaultNow(),
})

export const crewMembers = pgTable('crew_members', {
  id: uuid('id').primaryKey().defaultRandom(),
  crewId: uuid('crew_id').notNull().references(() => crews.id, { onDelete: 'cascade' }),
  userId: text('user_id').notNull(),
  joinedAt: timestamp('joined_at', { withTimezone: true }).notNull().defaultNow(),
}, (table) => ({
  crewUserUniqueIdx: uniqueIndex('crew_members_crew_user_idx').on(table.crewId, table.userId),
  // Drives "my crews" on every page load.
  userIdx: index('crew_members_user_idx').on(table.userId),
}))

export const crewInvites = pgTable('crew_invites', {
  id: uuid('id').primaryKey().defaultRandom(),
  crewId: uuid('crew_id').notNull().references(() => crews.id, { onDelete: 'cascade' }),
  // Plaintext by necessity — see D3. 72 bits, base64url.
  token: text('token').notNull().unique(),
  // Immutable here, unlike crews.keeperId — an invite is attributed to whoever
  // minted it even after the keeper changes.
  createdBy: text('created_by').notNull(),
  expiresAt: timestamp('expires_at', { withTimezone: true }).notNull(),
  revokedAt: timestamp('revoked_at', { withTimezone: true }),
  revokedBy: text('revoked_by'),
  createdAt: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
}, (table) => ({
  crewIdx: index('crew_invites_crew_idx').on(table.crewId),
}))

export const crewMutes = pgTable('crew_mutes', {
  id: uuid('id').primaryKey().defaultRandom(),
  crewId: uuid('crew_id').notNull().references(() => crews.id, { onDelete: 'cascade' }),
  userId: text('user_id').notNull(),
  mutedAt: timestamp('muted_at', { withTimezone: true }).notNull().defaultNow(),
}, (table) => ({
  crewUserUniqueIdx: uniqueIndex('crew_mutes_crew_user_idx').on(table.crewId, table.userId),
}))
```

- [ ] Presence of a `crew_mutes` row **is** the muted state. No boolean column — unmuting deletes the row. Avoids the tri-state (`null` / `true` / `false`) that a nullable boolean invites.
- [ ] `memberCount` is **not** stored. It is `count(*)` over `crew_members`, and the cap check reads it under the D4 lock. A denormalized counter is a second source of truth for a number that is never larger than 12.
- [ ] Export from `packages/db/src/schema/index.ts`; export `$inferSelect` / `$inferInsert` types.

## Phase / PR-2 — `/v1/crews` router

`apps/api/src/routes/crews.ts`, mounted at `app.route('/v1/crews', crewsRouter)` in `apps/api/src/routes/index.ts`. `clerkMiddleware()` + `requireAuth` on `*`. **`requireFeature('crews')` is applied to the create route alone** (decision 6, D6).

### Task 1: `GET /v1/crews` — the crews list

- [ ] Crews where the caller has a `crew_members` row. For each: `id`, `name`, `patchSalt`, `memberCount`, up to 5 members for the cluster (`userId`, `handle`, `avatarColor`), `upcomingCount`, `isKeeper`, `muted`.
- [ ] `handle` and `avatarColor` join `user_profiles` (`packages/db/src/schema/user-profiles.ts:25-27`). `handle` is nullable and **stays nullable through the whole stack** — a member without one is counted and rendered as a letterless dot, never given an invented name (the #762 contract).

### Task 2: `GET /v1/crews/:crewId` — crew detail

- [ ] 403 unless the caller is a member. Membership is the authorization boundary for every read.
- [ ] Roster: all members with `handle`, `avatarColor`, `joinedAt`, `isKeeper`, `isYou`.
- [ ] `upcoming`: events dated today or later where **≥1** member has `attending_at IS NOT NULL`, ascending, each with the going-member list.
- [ ] `nights`: events dated before today where **≥2** members attended, descending, each with the attendee list.
- [ ] The `1` and the `2` are the tense rule (decision 2) and belong in one named constant each in `apps/api/src/lib/crew-shows.ts`, not inlined at two call sites where they can drift.

### Task 3: `GET /v1/crews/:crewId/shows` — the Browse lens feed

- [ ] Same upcoming predicate as Task 2, shaped to whatever Browse already consumes so the lens is a filter over the existing list rather than a parallel event model.
- [ ] Each row carries `crewGoingCount` and the going-member list. Row surfaces render the **count**; names are event-detail-only (decision 5).

### Task 4: `POST /v1/crews` — create

- [ ] The only route behind `requireFeature('crews')`.
- [ ] Body: `z.object({ id: z.string().uuid().optional(), name: z.string().min(1).max(40) })`. Optional client-supplied id per D2; PK conflict returns **409**.
- [ ] Insert the crew and the creator's `crew_members` row in one transaction. A crew with no members is unreachable forever.
- [ ] `patchSalt` starts at 0 and is never set by this route from user input.

### Task 5: Keeper-only mutations

- [ ] `PATCH /v1/crews/:crewId` — rename. Body `{ name }`. Does not touch `patchSalt`; assert this in a test, because "renaming rerolls the artwork" is exactly the bug the design forbids.
- [ ] `POST /v1/crews/:crewId/patch/reroll` — `patchSalt = patchSalt + 1`. Server-side increment, never a client-supplied value.
- [ ] `DELETE /v1/crews/:crewId/members/:userId` — remove a member. Keeper cannot remove themselves through this route (that is leave/handoff).
- [ ] `DELETE /v1/crews/:crewId` — delete. `onDelete: 'cascade'` clears members, invites, and mutes. Attendance rows in `user_events` are untouched: "the nights you went stay in your Concerts."
- [ ] All four share one `requireKeeper` helper returning **403** for a member and **404** for a non-member — a non-member must not be able to distinguish "crew exists, you're not the keeper" from "no such crew".

### Task 6: `POST /v1/crews/:crewId/leave` and `/handoff`

- [ ] Leave, non-keeper: delete the caller's membership row.
- [ ] Leave, keeper with other members: **409** with a typed code the UI maps to the handoff sheet. The server refuses; the client does not get to skip the step (decision 7).
- [ ] Leave, keeper alone: **409** with a distinct code that maps to the "you're the last one" delete confirm. Deletion stays an explicit second call.
- [ ] `POST /handoff` with `{ newKeeperId }` — keeper only, target must be a current member, sets `keeperId` and returns the updated crew.

### Task 7: Mute

- [ ] `PUT /v1/crews/:crewId/mute` inserts a `crew_mutes` row (`onConflictDoNothing`); `DELETE` removes it. Member-only, not keeper-only.

### Task 8: Integration tests

- [ ] 401 unauthenticated on every route. 403 for a non-member read. 403 for a member attempting a keeper mutation.
- [ ] Free-tier create returns 403 with `ENTITLEMENT_REQUIRED_CODE`; free-tier **list, read, leave, and mute all return 200** — this is the D6/decision-6 guard and the single most important test in the PR.
- [ ] Tense boundaries: a show with exactly 1 attendee appears in `upcoming` and **not** in `nights`; a past show with exactly 1 attendee appears in neither; a past show with 2 appears in `nights`.
- [ ] Rename leaves `patchSalt` untouched; reroll increments it by exactly 1.
- [ ] Keeper leave returns 409 while another member exists.

**Unblocked** — both gates resolved above on 2026-08-05. The join surface is authenticated for beta, so this phase is no longer a "public surface" phase; it is an authenticated one plus the funnel plumbing that returns a new arrival to the link.

### Task 1: Token minting

- [ ] `apps/api/src/lib/crew-invite-token.ts` — `randomBytes(9).toString('base64url')`, 12 URL-safe chars, ~72 bits. Follows the `generateCode()` shape at `apps/api/src/routes/admin/invite-codes.ts:13-17`.
- [ ] `POST /v1/crews/:crewId/invites` — any member may mint (decision: no gatekeeping inside a group of 12). Revokes any live invite for that crew first, so a crew has at most one live link and "Retire this link" means something. `expiresAt = now + 7 days`.
- [ ] Do the revoke and the insert in one transaction that takes `SELECT ... FOR UPDATE` on the `crews` row first — the same lock the join path uses (D4). Revoke-then-insert without it does **not** give "at most one live link": two members minting concurrently both read zero live invites and both insert. A partial unique index cannot substitute, because liveness depends on `now()` against `expires_at`.
- [ ] `GET /v1/crews/:crewId/invites/current` — the live invite or `null`. Members only.
- [ ] `POST /v1/crews/:crewId/invites/:id/revoke` — any member. Sets `revokedAt` / `revokedBy`.

### Task 2: `GET /v1/crew-invites/:token` — resolution

- [ ] **Authenticated.** This changed when gate (a) resolved: the join page is auth-gated, so there is no signed-out consumer of this endpoint, and shipping it unauthenticated would add a public surface nothing calls. Keep the shape ready for a launch-time flip to public, but do not ship the flip on a guess.
- [ ] Returns `PublicCrewInvite` (PR-1 Task 5) for a live token.
- [ ] Expired, revoked, and unknown tokens all return **404** with a `reason` of `expired | revoked | unknown`. A dead link renders no crew identity at all (decision 11), so the 404 body carries no crew fields — `reason` is the entire payload.
- [ ] At-cap is **not** a dead link: it resolves normally with `isFull: true`, because the design keeps crew identity visible and swaps the CTA.
- [ ] Rate-limit with the existing `apps/api/src/lib/rate-limit.ts`, keyed `crew-invite:${userId}` now that the route is authenticated — a Clerk id is a better key than an IP, and it sidesteps the `x-forwarded-for` derivation entirely. 72 bits is only strong if enumeration is also expensive. One caveat belongs in the code comment: the limiter is in-memory and per-instance, so it is a speed bump, not a guarantee, once the API runs more than one instance. If this endpoint is ever flipped public, the key has to fall back to the IP derivation in `apps/api/src/routes/waitlist.ts` (`.split(',')[0]?.trim() ?? 'unknown'`) — do not invent a second convention at that point.

### Task 3: `POST /v1/crew-invites/:token/join`

- [ ] Authenticated, **not** entitlement-gated.
- [ ] In one transaction: `SELECT ... FOR UPDATE` the crew row (D4), re-validate the token, count members, insert. **409** at 12. Already-a-member is a **200** no-op, not an error — a forwarded link tapped twice is not a failure.

### Task 4: The leak test

- [ ] An integration test that seeds a crew whose members are attending events, resolves the token as an **authenticated user who is not a member of that crew** — the joiner's actual state, now that Task 2 is authenticated — and asserts the serialized response body contains **no event id, no artist name, no venue name, and no date**. Decision 4 is a privacy promise made in copy on the landing page ("We're not showing you what they're going to until you're in"); this test is what keeps it true.

### Task 5: Middleware and the return-path funnel

- [ ] **Add `/crew/join(.*)` to neither public matcher.** The correct change to `middleware.ts` is *no change at all* to `isAlwaysPublic` / `isPublicOnceLaunched` — the route falls through to `auth.protect()` and gets `redirect_url` for free. Write a middleware test that pins this, so a later reader does not "fix" the missing entry by adding one.
- [ ] Test that a signed-out visitor to `/crew/join/abc` is redirected with `redirect_url=/crew/join/abc` intact, and that `/crews`, `/me`, and `/admin` still redirect too. `/crew/join` and `/crews` differ by one character; neither is public.
- [ ] Carry the return path through the beta funnel (gate (b)). Four edits, in this order:
  - [ ] `middleware.ts:194-199` — when bouncing an invite-gated route to `/auth/code`, attach a `redirect_url`. Take the **incoming** `redirect_url` param when one is present, and only fall back to `toSafeReturnPath(pathname, search)` when it is not. The order matters: the only invite-gated matcher is `/sign-up(.*)`, so a visitor reaching this branch is already on `/sign-up?redirect_url=/crew/join/<token>` — the path itself is `/sign-up`, and `toSafeReturnPath` alone would return the visitor to the sign-up screen (or bounce a now-signed-in user to `/events`) instead of the crew link. Sanitise the forwarded param with `sanitizeReturnPath` before reusing it; it arrived from the querystring and is attacker-controllable.
  - [ ] `apps/web/src/app/auth/code/actions.ts` — read that param, run it through `sanitizeReturnPath` (`lib/auth/intent.ts:74`), and write it into a second signed cookie next to `invite_verified`, reusing `signInviteCookie` and `INVITE_COOKIE_SECRET`. A query param cannot cross Clerk's screens; this cookie can.
  - [ ] `apps/web/src/app/auth/complete/page.tsx:54` — replace the hardcoded `redirect('/events')` with the cookie's value when present, clearing the cookie in the same pass. `/events` stays the fallback, so a visitor with no pending return path is unaffected.
  - [ ] Re-sanitise on read, not only on write. The cookie is signed, but `sanitizeReturnPath` is cheap and a redirect target read from a cookie is still a redirect target.
- [ ] Integration test for the whole chain: unauthenticated visitor hits `/crew/join/<token>` → `/auth/code` → submits a valid beta code → completes signup → lands back on `/crew/join/<token>`, not `/events`. This is the test that proves gate (b) shipped; without it the plumbing is four edits nobody exercises.
- [ ] Negative test: a hostile cookie value (`//evil.com`, `/\evil.com`) yields `/events`.
