# Stale price — "still accurate" confirmation — Implementation Plan

**Ticket:** none. Intake from Hugh's testing session, 2026-08-21. Phase **beta** · Priority **normal**.
**Product decision on file:** *any user can confirm*, not just the original submitter (Hugh, 2026-08-22).

**Reported as:** *"There's no way for a user who originally submitted a price to mark that price as still accurate when the system has flagged it as stale."*

**Goal:** Give a stale price a way back to fresh that does not require someone to re-submit the same number. One new pair of columns, one new route, one affordance on the surfaces that already render the stale stamp.

**Architecture:** Additive nullable columns on `price_submissions` (expand-only, no backfill). One new API route. The staleness fix is one *rule* applied at each place a freshness timestamp is derived — there turn out to be two, plus four query projections that must carry the column. An earlier draft of this plan claimed a single expression covered everything; §"The freshness timestamp" below records why that was wrong and what the real surface area is.

---

## The report names the third-smallest of three defects

Hugh's sentence points at the self-confirm guard. That guard is real (`apps/api/src/routes/price-submission-confirms.ts:82-86`, 403 when `submission.userId === userId`) and Hugh's decision moots it. But removing it alone fixes nothing, because two larger things sit underneath. **Read this section before the task list.**

### 1. There is no confirm affordance on a stale price for anyone

`SubmissionList.tsx:86-95` renders the Confirm button only when `!isOwn && !submission.byYou && isPending` — the `!isOwn` half is the outer branch at `:84`, and it is worth separating from `byYou`, which tracks only whether the viewer has already corroborated. Ownership and prior confirmation are different exclusions and the button needs both to pass. A price that has gone stale is `corroborated`, not `pending`, so the button is not merely disabled for the submitter — it is not rendered for anybody. The report says "no way for the submitter"; the truth is no way for any user, submitter or not.

**A caveat that strengthens the point rather than weakening it: this component is not currently on screen at all.** `SubmissionList`'s only importer is `VerifySheet.tsx`, and `VerifySheet` has no call sites anywhere in `apps/web` — they are a dead *pair*, not a live surface. Review floated this as "SubmissionList may be dead code," which is half right and worth stating precisely, because it changes what the file is evidence *of*. It is not a broken button a user can find; it is the codebase's only written expression of when a confirm is offered, and it says `isPending`. PR-B builds a new affordance on live surfaces and should not resurrect either file.

### 2. Confirming would not clear the badge even if the button were there

Staleness is timestamp-based, not action-based:

- `apps/web/src/components/consumer/lib/staleness.ts:14-21` — `isPriceStale(observedAt)` is `Date.now() - observed > STALE_AFTER_MS` (24h).
- `apps/api/src/lib/price-aggregation/aggregate-by-tier.ts:116` — `observedAt: row.createdAt.toISOString()`.
- `apps/api/src/routes/events.ts:959` — the *other* derivation, on the flat legacy response shape: `priceObservedAt` from `legacyPrimary.createdAt`.
- `price_submissions.createdAt` is written once on insert and never again.

`updatedAt` is not a freshness field either, and not for the reason an earlier draft of this plan gave. It does **not** move only on a status transition: `price-submission-confirms.ts:136` writes `updatedAt: sql\`now()\`` on every successful confirm. (Every such confirm is on a pending submission — `:75-80` rejects anything else first — so this is a narrower statement than "any confirm," but still wider than "status transitions only.") It is also load-bearing elsewhere — `pick-tier-headline.ts:36` tie-breaks equal prices by it, and `aggregate-by-tier.ts:117` exposes it as `approvedAt`. So it is unusable here in the opposite direction from what was first written: not too still, but already spoken for.

So `observedAt` is an immutable creation timestamp wearing an observation timestamp's name. The confirm route increments `corroborationCount` and, at threshold, flips `status` — it writes no timestamp the staleness check reads. **A confirm on a stale price is currently a no-op as far as the badge is concerned.** There is no existing write path anywhere that refreshes an already-approved price's freshness; the only escape today is a brand-new submission with a newer `createdAt`.

**Consequence:** the work is not "let the submitter press the button." It is "give the system a freshness timestamp, and an action that writes it."

### 3. The two confirms are different actions wearing one name

The existing confirm is a **corroboration vote**: it moves a price from pending to live, it counts toward a threshold (`SP_POLICY.confirmsRequired` = 2, rising to `SP_POLICY.confirmsRequiredImminent` = 3 within `imminentThresholdDays` of the show — `packages/types/src/index.ts:257-264`), and it is one-per-user-forever — `submission_confirms` carries `UNIQUE(submissionId, userId)` (`packages/db/src/schema/submission-confirms.ts:21-24`).

What Hugh is asking for is a **fresh sighting**: it changes no price, grants no approval, and recurs — the same person may legitimately re-check the same price every week for a month. Routing it through `submission_confirms` would collide with that unique constraint on the second sighting, and would corrupt `corroborationCount` if not carefully guarded.

They are therefore separate paths, and the self-confirm guard belongs to only one of them. For corroboration it is a genuine anti-sockpuppet property: you cannot vote your own price into being live. For a fresh sighting there is nothing to vouch yourself into — the price is already approved, and the submitter is frequently the best-placed person to look again. That is why Hugh's *any user can confirm* is the right call rather than a relaxation.

## Design

### The freshness timestamp

Two nullable columns on `price_submissions`:

| Column | Type | Meaning |
| --- | --- | --- |
| `last_seen_at` | `timestamptz` null (`withTimezone: true`) | When someone last reported seeing this price still on sale |
| `last_seen_by` | `text` null | Clerk user id of that person, for admin abuse review |

`withTimezone: true` is not optional decoration: every other persisted timestamp on this table carries it (`packages/db/src/schema/prices.ts:137-146`), and a bare `timestamp` would make the `now()` comparison in the staleness predicate depend on the session timezone. The 24-hour window would then be correct only by luck.

**⚠️ Adding `last_seen_by` to the table publishes it, because one consumer route returns `price_submissions` rows whole.** `GET /v1/submissions/:id` (`apps/api/src/routes/submissions.ts:17-30`) is `db.select().from(priceSubmissions).where(eq(id))` with no projection, returned as `data: submission` behind nothing but `clerkAuth` + `requireAuth`. Submission ids are public — they ship in `TierHeadline` (`packages/types/src/index.ts:695`) — so any signed-in user can read any submission row by id. A new column on this table is therefore public by default, and calling `last_seen_by` an admin-only field is only true if PR-A *makes* it one. **PR-A replaces that `select()` with an explicit column list omitting `last_seen_by`, and carries a test asserting the field is absent from the response.**

Two things follow that are worth stating rather than leaving for the implementer to notice. First, `last_seen_at` stays in the projection: it is a timestamp, not an identity, and it is already implied by the stale badge the reader can see. Second, **this route leaks `price_submissions.user_id` — the submitter's own Clerk id — today**, by the same `select()` and to the same audience. That is a pre-existing exposure this plan did not create and does not scope, but the one-line fix it requires is the *same* line: once the projection is explicit, dropping `user_id` from it costs nothing. PR-A should do both and say so in its description. Naming it here so it is a decision rather than an oversight.

**`last_seen_by` holds a Clerk id, which drags in the account-deletion cascade.** `USER_DATA_REGISTRY` (`packages/db/src/user-data-registry.ts:120-137`) currently declares `price_submissions` with `userIdColumn: 'user_id'` and an empty `otherUserIdColumns`, and an integration test (`apps/api/src/lib/user-data.integration.test.ts:146`) asserts that every column looking like it holds a Clerk id is declared. So PR-A must add `last_seen_by` to `otherUserIdColumns`, or CI fails — which is the good outcome, because declaring it is only half the job.

**Export is a separate decision from deletion, and both new columns are excluded.** `exportColumns` (`user-data-registry.ts:125-134`) is an allowlist, so neither field ships in a data export unless someone adds it — but a default is not a decision, so record it: `last_seen_by` is another user's identity and can never be exported; `last_seen_at` is excluded too, because on your own submission it records *someone else's* act of vouching, not anything you authored. The entry's `reason` (`:135-137`) currently reads "Corroboration counts belong to other users," which was written when that was the only other-user data on the table. PR-A extends it to name sightings, so the registry keeps explaining every excluded field rather than just the original one.

**Whether it must also be *nulled* is answered by a rule already written down, not by judgment.** Declaring a column in `otherUserIdColumns` does not disposition it; the registry loop skips those entirely, and `user-data.ts:73-82` states the policy: *"most name an ADMIN who acted and stay put as the record of who did it… Revoking is an ordinary member action, so the revoker's Clerk ID is their personal data and goes with them."* That is the test, and it is not "is this an actor column." **Eight** other actor columns are declared and deliberately kept, across seven tables — `user_roles.granted_by` (`user-data-registry.ts:66`), `gifted_comps.granted_by` (`:340`), `audit_log.target_id` (`:364`), `venues.verified_by` (`:381`), `crawl_triggers.triggered_by` (`:419`), `venue_fault_acknowledgements.acknowledged_by` (`:460`), and `invite_codes.created_by` and `revoked_by` (`:472`) — every one an admin act. `crew_invites.revoked_by` (`:193`) is nulled because it is not. Two earlier drafts put this number at four and then at five; it is eight kept out of nine declared, and the ratio is the point: retention is the overwhelming default and a member-action column is the rare exception being claimed here.

A sighting is an ordinary member action by any signed-in user. It falls on the `revokedBy` side, so **`last_seen_by` gets a hand-written null in `deleteUserData` alongside it**, and PR-A owns both halves. An earlier draft got the right answer by calling `revokedBy` the function's "one hand-written exception," which review correctly flagged as false — it is one of nine declared actor columns and the only *member-action* one. The conclusion survives the correction; the reasoning it rested on did not.

**PR-A also has to edit the comment that states the rule.** `user-data.ts:73-82` currently says `crewInvites.revokedBy` is *the* one that does not stay put. After this change there are two, so leaving that prose intact would make the file's own documented contract contradict the code three lines below it — and this plan's entire justification for nulling `last_seen_by` is that comment being authoritative. Rewriting a policy comment while relying on it is not optional bookkeeping.

**A per-user lock against the deletion race is declined.** `DELETE /v1/users/me` cleans the database before deleting the Clerk account (`users.ts:444-447` — the ordering is real), so an in-flight sighting can commit its write after cleanup. The window is real and it is not new: `crews.ts:915` writes `revokedBy` unconditionally with no guard, and that is the closest comparison precisely because it is the other member-action column with the same nulling obligation. Serializing here and not there would make this route the sole holder of a convention while leaving the identical window open next door. What the window actually leaves behind is a Clerk id that no longer resolves, which admin review reads as a deleted user rather than as someone else. If the promise in `user-data.ts:29-33` is to be tightened to cover in-flight writers, that is one change covering both columns, and it is worth raising as its own piece of work rather than smuggling in here.

The rule is **the later of the two**, and it must be a max rather than a coalesce:

```ts
observedAt: maxDate(row.lastSeenAt, row.createdAt).toISOString(),
```

`row.lastSeenAt ?? row.createdAt` would be wrong: any non-null `lastSeenAt` wins under `??`, so a sighting written before `createdAt` — a clock skew, a backfill, a repaired row — would move the badge *backwards*. The write path should never produce that, which is exactly why the read path should not depend on it not happening.

**This is not a one-line change, and the surface area is the main thing PR-A has to get right.** `lastSeenAt` is not currently in the aggregation input at all. `TierRow` (`pick-tier-headline.ts:3-12`, **not** `aggregate-by-tier.ts` — that file only declares `CorroboratedTierRow extends TierRow` at `:19-22`, so the field has to be added in the base interface a directory over) and `CorroboratedSubmissionRow` (`build-price-by-tier.ts:13-26`) declare only `createdAt` and `updatedAt`, and every query feeding them uses an explicit select list, not `select(*)`. So PR-A must touch:

| Site | Change |
| --- | --- |
| `packages/db` schema + migration | The two columns |
| `TierRow` (`pick-tier-headline.ts:3-12`) / `CorroboratedSubmissionRow` | Add `lastSeenAt: Date \| null` |
| `load-price-by-tier.ts:19-32` | Add the column to the select |
| Event-detail projection | Same |
| `venues-public.ts:302-315` | Same |
| `aggregate-by-tier.ts:116` | The max expression |
| `events.ts:959` | The **second** derivation: `priceObservedAt` on the flat legacy shape, from `legacyPrimary.createdAt`. Same max rule. Missing this leaves `PriceDisplay` and `DisputedPriceCard` stale while the tier surfaces clear |
| `build-price-by-tier.ts:52-72` | **The mapper, not just the query.** It builds each `TierRow` field-by-field across ten explicit properties; a required `lastSeenAt` that the select fetches but the mapper drops fails typecheck at best and silently reads `undefined` at worst |
| `venues-public.ts:333-348` | The second mapper, same field-by-field shape, same fix |
| Admin submissions projection (`prices.ts:260-284`) | Add both columns — see the abuse note under the route |
| `PriceSubmissionHistoryRow` (`apps/web/src/lib/queries/use-admin-price-submissions.ts:17-32`) | The client-side admin type, which has no last-seen fields; without it the new columns cannot reach the admin table |

**Two shared-type changes ride along, and neither is optional.** `EventDetailResponse` (`packages/types/src/index.ts:771-868`) carries the flat price fields but no submission id, so the flat path cannot pass one to `PriceDisplay` type-safely until that response type gains the field and its fixtures follow. And `PriceDisplayProps` has no prop to receive it. Naming these here because "add the column to the projection" reads like a query edit and is in fact a contract edit.

The consumer components need no change: once `observedAt` is right, `StaleStamp` on event detail, `WatchingShow.priceObservedAt` and `RowPrice.observedAt` all clear on their own. That much of the original claim survives. What did not survive is the idea that the *producer* side was one expression.

`observedAt` is still the semantically honest home: it was always meant to be "when this price was seen," and a sighting is exactly that. We are not overloading the field, we are finally supplying it.

**No new table.** Per CLAUDE.md's KISS rule, exhaust existing fields first. A `price_sightings` history table would buy an audit trail; the accepted tradeoff is that the existing dispute path covers the abuse case, with `last_seen_by` as a lead for a human rather than a signal — see the abuse note under the route for what that column can and cannot show. History can be added later without a rewrite, because the columns are additive.

### The route

`POST /v1/events/:id/price-submissions/:submissionId/still-accurate`, separate from the confirm route rather than a mode flag on it. They have different guards, different preconditions and different success semantics, and folding them together is how the corroboration count gets corrupted by a sighting.

**Empty body.** An earlier draft required a `howFound` enum. Two things kill that. First, it is not the existing contract it claimed to be: confirm takes `method: z.enum(['same-vendor', 'other-vendor', 'box-office'])` (`price-submission-confirms.ts:15-17`), not `howFound`. Second and decisive, the two proposed columns have nowhere to put the answer, so a required field would either be discarded on receipt or, worse, written to the original submission's `howFound` and corrupt its provenance. Asking a question you throw away is not an honesty rail. The action is one tap; if we later want the method, it arrives with the history table and a column to hold it.

**Empty means no body validator at all, and the path params are checked inline.** Review asked for a strict empty-object Zod schema plus `zValidator('param', ...)` on both UUIDs, citing `admin/events.ts:631`. Both halves are the *admin* convention. Consumer siblings with no meaningful body omit the body validator entirely (`attending.ts:53`, `watching.ts:120`), and they validate path params with a raw `ctx.req.param()` read followed by an inline `uuidSchema.safeParse` (`attending.ts:58`, `watching.ts:125-126`). The reviewer's underlying point still lands, though: the confirm route this plan models on validates its body but **not** its params (`price-submission-confirms.ts:39`), and inheriting that silently would let a malformed id reach Drizzle and turn a client error into a 500. So this route does what the consumer siblings do — `safeParse` both `:id` and `:submissionId`, 400 on a malformed one, no body schema.

**Review has now asked four times for a strict empty-object body validator, most recently on the grounds that "callers can send arbitrary JSON and the route silently accepts it."** The answer is unchanged, and the fourth ask deserves the precedent rather than the argument, because the precedent settles it. **The two path-only sibling POSTs in the consumer API both omit the json validator**: `artist-follows.ts:56-59` (`POST /:slug/follow` — param validator, feature gate, no body schema) and `event-reports.ts:274-278` (`POST /:id/reports/:reportId/confirm` — auth guards, a raw `ctx.req.param()` read, no body schema). Both are auth-gated writes taking their entire input from the path, which is precisely this route's shape. Two sibling implementations settle a convention, and this route conforms to them. They are the closest analogues rather than the only consumer writes without a body schema — `events.ts:1323` and `notifications.ts:264`, `:292`, `:329` also omit one, which makes the pattern broader still but those routes a looser match on shape.

The reasoning underneath that convention, for whoever asks a fifth time: nothing is silently accepted because nothing is read. The handler never touches the body, so an unread payload has no path to any behaviour, any query or any log. A strict schema converts a request that is currently ignored into a 400 — a *stricter* contract, not a safer one, buying strictness over a field that does not exist. The security property being reached for is "no unvalidated input reaches the DB," and this route holds it by having no body input at all, which is stronger than validating one. CLAUDE.md's Zod rule governs input that is used. If a later change gives this route a body, the validator arrives with it.

Guards, in the order the route runs them — the first two are lifted from the confirm route, which already gets this right:

| Guard | Rule | Why |
| --- | --- | --- |
| Auth | Signed in | Same bar as confirm |
| Event visibility | Event must exist, `hiddenFromConsumer = false`, `firstMissingAt IS NULL` **and** its venue must be `active` | The confirm route checks only the first (`price-submission-confirms.ts:47-51`). Given its own comment says hidden events are treated as not found "everywhere else in the consumer API," that narrower check reads as an oversight rather than a decision, and this route should not inherit it. Otherwise an event the crawler has lost 404s to readers while still accepting freshness writes. **The venue half was missed by two earlier drafts of this plan, which both wrote the contract as two flags.** It is three: `events.ts:615-632` reaches the event through `.innerJoin(venues, and(eq(events.venueId, venues.id), eq(venues.active, true)))` at `:618` before the `where` at `:627-632` ever runs, so deactivating a venue removes its whole catalogue from event detail without touching a single event row. That is the *cheapest* way for an event to become invisible and the only one of the three that leaves no trace on the event itself |
| Event scoping | Submission must exist **and belong to `:id`** | `price-submission-confirms.ts:58-73`. Without it a caller refreshes a submission on an unrelated or hidden event by passing any event id they like |
| Status | Submission must be `corroborated` | A `pending` price already has the corroboration path; a sighting must not become a second way to approve one |
| Staleness | Reject unless the price is currently stale | Stops anyone pre-emptively pinning a price fresh, and doubles as a per-submission cooldown — **not** a per-caller rate limit, which this route deliberately does not have; see below |
| Self | **None** | Hugh's decision, reasoned above. Note this is the one guard the confirm route has that this route deliberately drops |

**Status codes are fixed, not a choice at build time, and they follow the confirm route rather than inventing a scheme.** That route already distinguishes the two cases: `400` for a submission in the wrong status (`price-submission-confirms.ts:76-78`), `409` for a conflict with existing state (`:169-182`). So: `401` unauthenticated; `404` unknown event, unknown submission, or a submission that does not belong to the event (one code, so the route does not leak which submissions live on which events); `400` for a submission that is not `corroborated`; `409` for a price that is not yet stale, which is a conflict with the current freshness window rather than a malformed request. Body is the house shape, `{ success: false, error: string }` with a human-readable message — no error-code enum, because none of the sibling routes have one and a new one would be a convention of size one.

**The staleness guard is the cooldown, and it only holds if the check and the write are one statement.** A read-then-update lets two concurrent callers both observe the stale value and both succeed. So the write is a single conditional update:

```sql
UPDATE price_submissions ps
   SET last_seen_at = now(), last_seen_by = $userId
  FROM events ev
  JOIN venues vn ON vn.id = ev.venue_id
 WHERE ps.id = $submissionId
   AND ps.event_id = $eventId
   AND ev.id = ps.event_id
   AND ev.hidden_from_consumer = false
   AND ev.first_missing_at IS NULL
   AND vn.active = true
   AND ps.status = 'corroborated'
   AND GREATEST(ps.last_seen_at, ps.created_at)
       < now() - make_interval(secs => $staleAfterMs / 1000.0)
```

**The window is a parameter, not a literal, and that is not fussiness.** An earlier draft hardcoded `interval '24 hours'`. The reader's side of this contract is `STALE_AFTER_MS` (`staleness.ts:14`), and the two numbers have to agree or the route rejects prices the badge calls stale (window too long) or accepts ones it does not (too short) — a bug with no symptom on either side alone, only in the gap between them. `staleness.ts` lives in `apps/web` and the route in `apps/api`, so PR-A either lifts the constant into `packages/types` and imports it both places, or leaves it duplicated **and adds a test asserting the two are equal**. The first is better; the second is the floor. What is not acceptable is a bare `24 hours` in SQL, because nothing then fails when someone tunes the badge.

Note the `make_interval` rather than string-building an interval. A draft wrote `($staleAfterMs || ' milliseconds')::interval`, which does not work: `||` is text concatenation, so a numeric bind parameter raises an operator/type error rather than producing an interval. `make_interval(secs => …)` takes a number directly and needs no cast.

**Every predicate in that `WHERE` is re-checked here on purpose, none of them redundantly with the guards above.** The guards run against a snapshot; this statement runs against the row it writes. Each column named is one another writer can move underneath the request:

- **`event_id`** — `priceSubmissions.eventId` is mutable: an admin event merge reassigns it (`admin/events.ts:1382-1386`). A merge landing between the membership check and the write would let a request for the old event stamp a submission that now belongs to another one.
- **`status`** — the corroboration path can promote a row concurrently.
- **`hidden_from_consumer`, `first_missing_at` and `venues.active`** — the joins to `events` and `venues` exist only to re-assert the visibility guard, which an earlier draft checked once in the preflight and then dropped. `hidden_from_consumer` moves when an admin hides or unhides (`admin/events.ts:1169`, `:1216`), which is rare; `first_missing_at` moves *from the crawler* (`crawl.ts:1449` sets it, `:316` clears it) on a job that runs every ten minutes. That second one is not a theoretical interleaving. `venues.active` is the rarest of the three but the widest-blast: one admin toggle takes an entire venue's catalogue out of view at once, so a batch of in-flight sightings all lose validity on the same write. Without these predicates a request can stamp freshness onto an event that stopped being visible mid-flight, which is precisely the state the guard exists to refuse.

**What those joins do not do is lock the event or the venue, and the plan should say so rather than imply otherwise.** `UPDATE … FROM` takes a row lock on the `price_submissions` target only; the joined `events` and `venues` rows are read at the statement's snapshot. So a hide or a `first_missing_at` write committing *inside* the statement's execution is not seen. The predicate collapses the window from preflight-to-write — many milliseconds, easily spanning a crawler tick — down to the width of one statement, and that is the whole of what it buys. Closing the remainder means `SELECT … FOR SHARE` on the event row, taking a lock on a table the crawler writes in bulk, to prevent a sighting on an event that went invisible microseconds ago. **Accepted, not fixed.** The residue is one stale-freshness stamp on a row nobody can currently see. **It does not self-heal, and an earlier draft claiming "the next sighting or crawl corrects it" was wrong on the crawl half**: the crawler writes `events.lastSeenAt` and `events.firstMissingAt`, never `price_submissions.last_seen_at`, so nothing on the crawl path touches this value. If the event becomes visible again with the same corroborated submission, the bad stamp is still there. Only a later sighting on that submission, or a different row winning the headline, changes it. That is a smaller residue than a self-healing one but it is the honest description, and the cure still contends with the crawler on a hot table. Recorded so a later reader knows the narrowing was deliberate and knows where the floor is.

**A zero row count says "no," not "why."** It cannot separate not-corroborated from not-stale from event-now-hidden from *someone else won the race two milliseconds ago*. So the error path does a second, non-authoritative read purely to choose the status code, exactly as `admin/founder-window.ts` does for its own conditional update (`:121-130` — conditional update, row-count check, follow-up read, classify). The conditional update stays the only success gate; the follow-up read only labels the failure. **That read must re-apply the event and visibility predicates, not look the submission up by id alone** — otherwise a row that moved to another event, or an event that just went hidden, gets classified as 400 or 409 and the response confirms the submission exists on an event the caller can no longer see. The classification read answers in the same order the guards do, so a lost race on freshness returns the same 409 a slower racer would have got, and everything else returns its own guard's code.

One statement on the success path, no transaction, no cooldown table, no per-user throttle. This is the main reason the design needs no history table, and it is worth a concurrency test.

**Calling it "the rate limit" overstates it, and the plan should use the accurate name.** It is a **per-submission cooldown**: it bounds how often *a given price* can be refreshed, and says nothing about how often *a given caller* can act. Those come apart badly, because `submissionId` ships in the public `TierHeadline` (`packages/types/src/index.ts:695`). One account can therefore walk the catalogue, refresh every stale submission once, and repeat daily — every call individually legitimate under the cooldown, the aggregate effect being that nothing on the site ever looks stale again. That is a different and larger failure than the single-wrong-price case in the abuse note below, because it degrades the staleness signal *everywhere* rather than lying about one number.

**Accepted for now, named rather than mitigated, and here is the reasoning to overturn later.** A per-user daily budget with a 429 is maybe thirty lines and no new table, so this is not a cost objection — it is that any threshold is a guess right now. Nobody has ever confirmed a price in this product, so we have no distribution to set a cap against, and a cap set too low silences the honest heavy user this feature is built for. The signal to build it is the first account whose sighting count is an order of magnitude above the median, which `last_seen_by` in the admin table makes visible. **Revisit at the point that column shows one.** What makes deferring defensible rather than negligent is that the damage is fully reversible: sightings write one nullable timestamp, so unwinding an abusive run is a single `UPDATE … SET last_seen_at = NULL WHERE last_seen_by = $userId`.

Residual abuse case: one determined actor refreshes a wrong price every 24h indefinitely. Mitigations: the price check ("Update") path lets any other user dispute it, and `last_seen_by` gives admin review a name to look at — **but only if the admin projection carries it.** `prices.ts:260-284` is an explicit field list, so PR-A adds both columns there and to `PriceSubmissionHistoryRow` — **and then adds a column to the admin table itself**, `PricesSubmissionsClient.tsx:463-545`, which today renders event, price, user, status, created-at and the action buttons and has nowhere for a last-seen actor to appear. A field that reaches the API but not the screen is not legibility.

**But be honest about what that column can show.** Both fields are overwritten on every sighting, so admin sees *the last* actor and *the last* time, never the pattern. A user who refreshes the same wrong price every 24 hours for a month looks identical to one who did it once. So the earlier phrasing — that `last_seen_by` "makes the pattern legible" — overclaimed, and is withdrawn: the column identifies the most recent sighting and nothing more. Detecting repetition needs the history table this plan deliberately does not build. What is actually load-bearing against the abuse case is the dispute path, where any other user can contest the price. The column is a lead for a human, not a signal. Accepted rather than engineered against, and this is what "accepted" costs.

### The affordance

**The action needs a submission id, and that is what decides where it can go.** The stale stamp renders on more surfaces than can call this route, because most of them carry only a timestamp.

**Start from the stamp, not from the card — and then check the timestamp is actually populated.** Four earlier drafts of this section got the inventory wrong: `PriceDisplay` as the only home; then `MultiTierLiveCard` as primary with the other optional; then four sites; then five, by adding one that passes a timestamp it can never have. The count moved every time somebody looked, which is the signal that it must be derived rather than recalled. Exactly **two** components in `apps/web` render `StaleStamp`, and between them **four** render sites can show a badge. That set is the whole scope of PR-B:

| Component | Render site | What it gets | What it lacks |
| --- | --- | --- | --- |
| `MultiTierLiveCard` (`:143`) | `EventDetailClient.tsx:1054` — the `resale-headline` branch | `observedAt` | submission id |
| `MultiTierLiveCard` (`:143`) | `EventDetailClient.tsx:1368` — the `multi-tier-shipped` branch | `observedAt` | submission id |
| `PriceDisplay` (`:1468`) | `EventDetailClient.tsx:1866` — the flat live-price fallback | `priceObservedAt`, via `effectiveObservedAt` (`PriceDisplay.tsx:1082`) | submission id |
| `PriceDisplay` (`:1468`) | `EventDetailClient.tsx:1611` — the locally-promoted `confirmedSub` | `priceObservedAt={confirmedSub.submittedAt}` (`:1624`) | **nothing — it already has the id** |

**`EventDetailClient.tsx:922` is not a sixth site, and the reasoning that briefly put it in this table is worth keeping as a warning.** That branch (`no-price-resale`) does render `PriceDisplay` and does pass `priceObservedAt`, which is why it looks like the flat path at `:1866`. A draft of this plan added it on the argument that `no-price-resale` means *no tier data*, not *no price* — `decision-tree.ts:105-114` returns that kind when `priceByTier` is null or empty and a resale link exists, and the branch then passes the flat `event.ticketPriceMin`. That much is true and it is still the wrong conclusion, because **`priceObservedAt` cannot be non-null in that state.** `events.ts:844-854` builds `legacyPrimary` only when `allCorroboratedRows.length > 0`, and `:955-959` assigns `priceObservedAt` only inside `if (legacyPrimary)`. `priceByTier` comes from `aggregateByTier(...)` at `:1008`, fed by `allCorroboratedRows` — the *same array*. (`pickHeadlinesByTier` at `:839` is a different helper, for headline and counter selection; both read that array, so the conclusion is unchanged, but tracing the flat/tier relationship starts at `:1008`.) So empty tiers and a null `priceObservedAt` are the same condition seen twice, `StaleStamp` renders nothing, and there is no badge to clear. The flat price shown there is a crawler price, which has no `price_submissions` row at all.

The lesson is the one this section keeps re-learning: **a site passing `priceObservedAt` is not a site that stamps.** Four separate inventories of this table have now been wrong, and every error came from reading the prop list at the call site instead of the condition under which the value is populated.

**Event rows are a stale-price surface too, but not a `StaleStamp` one.** `row-chips.ts:98-106` emits a `freshness` warn chip off the same `isPriceStale` check, so a reader does see staleness on a row. An earlier draft's claim that nothing outside this table can show a stale badge was wrong, and is narrowed: the table enumerates the `StaleStamp` sites, which are the sites that can carry an *action*. Rows keep the chip and gain nothing, for the reason given below.

**And one branch sits in front of all five without appearing in the table.** `EventDetailClient.tsx:1487-1490` tests `event.counterSubmission != null && priceMin !== null && event.priceStatus !== 'soldout'` and returns `DisputedPriceCard` (`:1486-1523`) *before* the `MultiTierLiveCard` chain at `:1525+` is reached. That card receives the flat `priceObservedAt` as `liveSubmittedAt` and renders **no `StaleStamp` at all**. So the moment a stale price picks up a pending counter-submission, the badge silently vanishes and the affordance goes with it — not because either was suppressed, but because a higher-priority branch took the render.

This is the same class as the `MixedTierCard` gap recorded below and gets the same disposition: **not this plan's, and deliberately so.** A disputed price is already in a flow that resolves its accuracy; adding a "still accurate" button next to an open dispute would be two contradictory answers to one question. Recorded because a builder threading `submissionId` through four sites and testing on an event with a counter-submission will see nothing render and reasonably conclude the plumbing is broken.

Four corrections fall out of that table:

- **There are two `MultiTierLiveCard` call sites, not one.** The `resale-headline` branch at `:1054` stamps the same way the `multi-tier-shipped` branch at `:1368` does. Plumbing only the second leaves a stale resale/community headline stamped and unclearable. An earlier draft cited `:1185-1263` as the second site; that range is the `mixed-tier` branch rendering `MixedTierCard`, a different component entirely.
- **`PriceDisplay` is not optional.** An earlier draft allowed it to ship stamp-only if the plumbing looked disproportionate. It cannot: `:1866` is a live path, it renders a real stale badge, and shipping the feature with that badge unclearable is the exact defect this plan exists to fix, just on a different branch of the same screen. If the flat response genuinely cannot carry a submission id, the honest move is to narrow the *goal* explicitly, not to leave one third of the stamps inert.
- **The `:1611` site is the cheapest one, and two drafts in a row talked themselves out of it wrongly.** It renders `PriceDisplay` for `confirmedSub`, a submission the client has locally promoted past its confirm threshold, stamping from `confirmedSub.submittedAt`. Because it comes off `EventDetailResponse['pendingSubmissions']` it already carries `id`, so it needs no projection or type change — just the prop. A draft then removed it on the theory that a locally-promoted row is still `pending` server-side and would 400 every time. **That is backwards.** `localConfirms` is incremented only inside `if (res.ok)` (`EventDetailClient.tsx:1791-1796`), and the confirm route promotes to `corroborated` in the same atomic `UPDATE` that increments the count (`price-submission-confirms.ts:127-144`, a `CASE WHEN … >= confirmsRequired THEN 'corroborated'`). So by the time the client has counted enough confirms to render this branch at all, the row it is rendering has already been promoted by the very request that let it count. The name `pendingSubmissions` describes the payload's origin, not the row's current status. Render the action here like anywhere else.
- **The plumbing is the same shape at the first three, but `MultiTierLiveCard` needs more than an id.** `TierHeadline` already carries `submissionId` (`packages/types/src/index.ts:695`); the headline objects built at `:1054` and `:1368` pass floor, ceiling, tier, vendor and kind and drop it, so the id itself is a threading job. What the id alone does not buy is a callable route: `MultiTierLiveCardProps` (`multi-tier/MultiTierLiveCard.tsx:30-49`) declares `headline`, `alternates`, `reports` and `observedAt` and nothing else — **no `eventId`, no callback, no auth state.** The route path needs both ids, so PR-B adds an `eventId` prop and an action callback to that interface, which is a wider component change than "pass one more field." The flat path needs a projection change of its own before its threading can start. PR-B owns all of it.
- **The flat path's submission id must come off `legacyPrimary`, not off `priceByTier[0]`, and this is a correctness trap rather than a style preference.** The two picks use different orderings and the code says so in as many words: `events.ts:841-843` carries the comment *"Legacy vendor-trust ordering preserved for the flat shape during the PR 4 migration window. **May pick a different 'primary' than any per-tier headline does.**"* The flat sort is `vendorTrustRank` then `createdAt` descending (`:848-851`); the tier sort is `sourceCategory` trust, then `priceMin` ascending, then `updatedAt` descending (`pick-tier-headline.ts:30-36`). Taking the id from the tier headline while the stamp comes from `legacyPrimary` would POST against one row and read freshness off another, so the write succeeds and the badge does not move — a bug that looks exactly like the route being broken. PR-A adds `legacyPrimary.id` to the flat projection alongside the timestamp it already derives from that same row, and the two travel together from there.
- **Watching list** — **no action**, reversing the earlier draft. `WatchingShow.priceObservedAt` is derived from `lowestHeadlineObservedAt` (`build-price-by-tier.ts:120`), which returns a bare string; there is no submission id on that payload and inventing one is a wider contract change than the feature warrants. The parity rule is about mobile and desktop of the same surface, not about every list reaching feature-equality with detail. Watching rows link through to detail, which is where the action lives.
- **Event rows** — **no action.** The row is a reading surface whose meta slot holds chips, not buttons, and its chip budget is already contested (see `2026-08-15-event-row-overflow.md`).

- **Event detail, mixed-tier** — **no action, and it needs no stale-stamp change either, because it has none to begin with.** `EventDetailClient.tsx:1185-1263` passes a headline to `MixedTierCard` carrying vendor, tier, floor, ceiling and kind, and `MixedTierCard.tsx:29-118` has no `observedAt` prop and renders no `StaleStamp` at all — unlike `MultiTierLiveCard`, which takes `observedAt` and stamps at `:140-145`. So a stale community headline in the mixed-tier state is currently unmarked. **That is a real pre-existing defect and it is not this plan's.** Adding a refresh action to a surface that never told the reader anything was stale is the wrong order of operations; the stamp is the fix, and it wants its own change. Recorded here so the omission is a decision rather than a gap. `MultiSourceMultiTierCard` is the same case for the same reason (see the box-office note below), which makes two detail states with no staleness signal at all — worth fixing together, in a change that is about the stamp rather than about the action.

**Crawler prices never get the action.** They have no `price_submissions` row at all, so there is nothing to write `last_seen_at` to. The affordance is conditional on a submission id being present, which excludes them for free rather than by a separate check.

**Box office is exempt from staleness in *selection*, not in *display*, and that distinction settles the question.** Review raised it three times, finally producing the actual contract rather than a code comment: `2026-06-20-price-source-api.md:17` says **"Box-office is exempt from staleness. A corroborated `source_category = 'boxoffice'` row leads its tier regardless of age."** That is a merged, authoritative doc and it is not overrulable here — but read the whole rule. It governs which row *leads its tier*. The very next line of the same contract says **"PR 3 does not introduce a new staleness filter"** and hands the question on explicitly: *"let the Consumer UI surface the trust mark."*

So the two things that looked like a conflict are the contract working as written. `pick-tier-headline.ts:14-21` implements the exemption exactly — a trust rank returning `0` for box office (`:18-22`), so an old box-office row still leads. And `isPriceStale` (`staleness.ts:14-21`) ignores source category, so that row still gets stamped. **The badge is the trust mark the contract asked the UI to surface.** An earlier draft of this plan called the comment and the code disagreeing; they do not, and that reading is withdrawn.

The consequence for this plan is the plain one: a box-office price can be stale on screen by design, so it needs the same way out as any other price, and excluding it would strand the one badge the contract explicitly wanted shown. No source-category branch in the route, the derivations, or the affordance.

The remaining half of the objection dissolves against the table above. The one decision that routes on box office, `multi-source-mixed`, requires a box-office headline with a resale alternate (`decision-tree.ts:122-140`) and renders `MultiSourceMultiTierCard`, which accepts neither `observedAt` nor a submission id and renders no `StaleStamp` (`MultiSourceMultiTierCard.tsx:12-22`). **There is no stale badge in that state, so there is nothing for an action to clear.** The plan's earlier flat assertion is therefore withdrawn as the wrong shape of claim: the action follows the stamp, and source category never enters into it. Wherever a box-office price reaches one of the three sites in the table it gets the action like any other; where it reaches `MultiSourceMultiTierCard` it gets neither, which is consistent rather than contradictory.

**The action is auth-gated, not merely submission-gated.** The route requires a signed-in user, but `MultiTierLiveCard` has no auth state, so an affordance conditioned only on "a submission id exists" would render for anonymous readers and fail on click. Reuse the existing pattern rather than inventing one: `CorroborationSheet.tsx:436-445` checks `isLoaded && !isSignedIn` and routes to the sign-in gate. Note the `isLoaded` half in particular — reading auth state before Clerk has loaded is a bug this codebase has already shipped once.

Copy is **not specified in this plan** and goes through the `copy-review` skill at build time. Two constraints for whoever writes it: the locked vocabulary reserves **Price check** for the *dispute* flow, so this action must not borrow that phrase; and `pendingCardB`/`communityPriceChip` already establish `confirmed` as the antonym of `pending`, which this action must not muddy — it produces a *fresh* price, not a *confirmed* one.

## PRs

**PR-A — schema, propagation, route.** Migration adding the two nullable columns; the row-type and select-list changes across all four projections; the max expression at *both* derivation sites (`aggregate-by-tier.ts:116` and `events.ts:959`); `legacyPrimary`'s submission id added to the flat projection; the admin projection **and the admin table column**; the `deleteUserData` null plus the `user-data.ts:73-82` policy comment it invalidates; the registry `reason` extension and the explicit projection on `GET /v1/submissions/:id` that keeps `last_seen_by` off a public response; the new route with its six guards and its single conditional update; **mounting it** — `app.route('/v1/events', priceSubmissionStillAccurateRouter)` in `apps/api/src/routes/index.ts`, alongside the three existing `/v1/events` mounts at `:41-44`, because a Hono router is inert until mounted and a plan that says "the new route" hides that step; integration tests that build the app through `createApp()` rather than importing the router directly, so an unmounted router fails them. Ships inert — nothing calls the route yet, and the max is a no-op while both columns are null.

**PR-B — the affordance.** `submissionId` threaded through `EventDetailClient` to the **four stamp sites** (`:1054`, `:1368`, `:1866`, `:1611`), which for the flat path means adding `legacyPrimary`'s id to that projection as well; an `eventId` prop and callback on `MultiTierLiveCardProps`; the client mutation **and all five of its response states**; the action beside the stamp; copy through `copy-review`; component tests covering each site; and a `releases.ts` entry.

Spell the response states out, because "client mutation" hides them. On **200**, the badge and the action both have to go, and since `observedAt` is server-derived that means refetching rather than flipping local state. On **409**, the price is already fresh: someone else won the race, and the correct handling is the same visual outcome as success plus a refetch, *not* an error toast. The window is global, so a page open in another tab will hit this routinely rather than exceptionally. Leaving the action on screen after either response invites a retry that is guaranteed to fail.

**The refetch is `router.refresh()`, not `queryClient.invalidateQueries`, and an earlier draft of this plan prescribed the wrong one.** `EventDetailClient` holds no React Query query for the event — its data arrives as server-rendered props from `page.tsx:66`, which calls `fetchEvent(id, token)` on the server. There is no cache key to invalidate, so an `invalidateQueries` call would compile, run, and change nothing on screen; the badge would sit there after a successful write. The component already establishes the right pattern for exactly this, calling `router.refresh()` after its own mutations at ten sites (`:190`, `:201`, `:355`, `:456`, `:472`, `:712`, `:792`, `:1472`, `:1520`, `:2018`). Follow those.

**But `router.refresh()` alone does not fix the `:1611` site, and that site needs a second, explicit step.** Three of the four stamp sites read server-derived props, so a refresh re-derives them and the badge clears. The fourth does not: `localSubmissions` is `useState(event.pendingSubmissions ?? [])` (`EventDetailClient.tsx:405-407`), whose initializer runs once per mount and is *not* re-run when a refresh delivers new props. `visibleSubs` is that state verbatim (`:1588`), `confirmedSub` is picked from it (`:1597-1602`) ahead of every server-derived branch, and the stamp reads `priceObservedAt={confirmedSub.submittedAt}` (`:1624`) — a timestamp held entirely in client memory. So after a successful sighting the refresh lands, the server says fresh, and the locally-promoted row keeps rendering the old stamp and the action beside it, inviting a retry that 409s. **PR-B must reconcile that array against the refreshed `event.pendingSubmissions` (or drop the sighted row from it) as part of the 200/409 handling, and carry a test for this site specifically** — it is the one place where "hand the page back to the server" is not sufficient, and the only one where a passing test on the other three would hide it.

**200 and 409 are not the only reachable responses, and a draft that specified only those two was specifying the happy path twice.** The button renders off a server payload fetched at page load and can sit on screen indefinitely, so every guard the route has is reachable by the time it is clicked:

| Response | Cause after render | Handling |
| --- | --- | --- |
| `200` | Success | `router.refresh()`; badge and action both go |
| `409` | Someone else refreshed it first | Same as 200 — `router.refresh()`, no error toast |
| `400` | The row's status moved off `corroborated`, e.g. a dispute landed | `router.refresh()`; the surface re-renders into whatever state now applies |
| `404` | The event was hidden, went missing, or its venue was deactivated | `router.refresh()`; Next re-runs the server fetch, which 404s consistently |
| `401` | Clerk token expired on a long-open tab | Route to the sign-in gate, the same path `CorroborationSheet.tsx:436-445` uses |

The shape of that table is the point: **four of the five responses are `router.refresh()`.** The action's job is to hand the page back to the server and let it re-derive, not to reason about which failure occurred. Only `401` differs, because a refresh cannot fix a missing identity. There is no error-toast branch at all — every non-auth failure means the reader's view is out of date, and showing them the current state answers the question better than telling them the button did not work. PR-B tests all five.

Split this way because PR-A is independently correct and independently testable, and because a schema change landing on its own is easier to roll back than one entangled with UI. PR-A is materially larger than the earlier draft implied; if it wants splitting further, the seam is propagation-and-read (columns, projections, both max expressions) before route-and-write.

## Test plan

- **Aggregation:** `observedAt` falls back to `createdAt` when `lastSeenAt` is null; takes `lastSeenAt` when it is later; **a `lastSeenAt` earlier than `createdAt` leaves `observedAt` on `createdAt`** — the regression test for the coalesce-vs-max bug this plan originally shipped.
- **Both derivations:** the same three cases against the flat `events.ts:959` path, not only the tier path. These are separate code, so one passing does not imply the other.
- **Flat id and flat timestamp must name the same row.** Seed an event where the two orderings diverge — `legacyPrimary` and the per-tier headline resolving to different submissions, which `events.ts:841-843` warns is possible — and assert the flat projection's submission id is `legacyPrimary`'s. Without this fixture, taking the id from `priceByTier[0]` passes every other test in this list while POSTing against the wrong row.
- **Route, rejections:** 401 anonymous; 400 on a malformed `:id` or `:submissionId`; 404 unknown event, unknown submission, and a submission belonging to a different event; 409 on a price that is not yet stale.
- **Route, status guard — parameterize it across every non-`corroborated` status, not just `pending`.** The contract is an equality check, so a handler written as `if (status === 'pending') reject` passes a pending-only test while silently accepting `disputed`, `stale` and `archived` rows. A table-driven test over the whole enum is the same amount of code and actually tests the guard that was specified.
- **Route, the freshness predicate needs its own max-vs-coalesce test, separate from the aggregation one.** The SQL `GREATEST` and the in-memory `maxDate` are two independent implementations of one rule, so proving the mapper is right proves nothing about the route. Seed `createdAt` at 23h and `lastSeenAt` at 48h: the correct answer is **409** (the later of the two is inside the window), and a `COALESCE(lastSeenAt, createdAt)` implementation returns 200. That single fixture is the whole coalesce bug on the write side.
- **Route, the visibility guard needs three fixtures and not one.** 404 on a `hiddenFromConsumer` event; **404 on an event with `firstMissingAt` set**; **404 on a visible event whose venue is `active = false`**. Each of the three predicates can be dropped from the implementation while the other two tests still pass, so a single "hidden event 404s" test proves almost nothing about the guard — which is exactly the failure the guard table warns about, and the venue one is the half two drafts of this plan did not know existed.
- **Window parity:** assert the route's staleness interval and `STALE_AFTER_MS` are the same number. If PR-A shares the constant this is one import and a trivial assertion; if it duplicates it, this test is the only thing standing between the two copies. Either way it is cheap and it is the failure with no other symptom.
- **Route, acceptances — and these need two fixtures, not one row tested twice.** 200 for the original submitter, the regression test for the reported symptom; **200 for a different signed-in user, asserting `last_seen_by` holds that user's id.** Together they are what makes an accidental self-only or no-op implementation fail. But they cannot run sequentially against the same submission: the first sighting starts a 24-hour window that is *global*, not per-user, so the second call would correctly return 409 and the test would be asserting the opposite of the design. Give each its own stale submission (or reset `lastSeenAt` between them). The same-row second-user call keeps its own test, asserting the 409 — that is the rate limit, and it is worth stating as an acceptance-adjacent case rather than losing it in the merge.
- `corroborationCount` unchanged after a sighting.
- **Concurrency:** two simultaneous sightings on the same stale submission yield exactly one 200 and one 409, which is the assertion that the rate limit is real.
- **Account deletion:** seed a sighting by a second user, delete that user, assert `last_seen_by` is null. The existing registry test (`user-data.integration.test.ts:146`) only proves the column is *declared*; because `last_seen_by` is an `otherUserIdColumns` actor field it needs the hand-written branch in `deleteUserData`, and nothing else would catch that branch being missing.
- **Staleness:** a submission whose `lastSeenAt` is inside the window reads fresh on event detail and on an event row.
- **Admin, both halves, and both suites already exist so there is no excuse for skipping either.** `apps/api/src/routes/admin/prices.integration.test.ts` gets an assertion that the submissions projection returns `lastSeenAt` and `lastSeenBy`; `apps/web/src/components/admin/prices/PricesSubmissionsClient.test.tsx` gets one that the new column renders them. PR-A adds the columns to the projection, the shared row type and the table, and a change spanning three layers with assertions at none of them is how a field reaches the API and never reaches the screen — the exact failure the abuse note above says makes the column worthless.
- **Manual:** confirm on staging that a stale price's badge clears after one sighting, and that the action disappears for 24h afterwards.
