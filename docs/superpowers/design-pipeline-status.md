## Maintenance rules

**Update optimistically inside the same PR that changes state** — don't wait for a "cleanup" loop-back. Tracker freshness is what makes it useful; a stale tracker is a lie about what's ready to pick.

**When to update:**

- A design brief merges → move ticket from 🎨 (brainstorm) to 📐 (awaiting Design handoff production) + add ✅ Recently shipped entry for the brief PR
- Claude Design produces a handoff → move from 📐 to 🎨 (audit in flight)
- A Readiness Review verdict lands → move handoff to 🟢 (Green), 🟡 (Yellow), or leave in 🎨 (Red / re-pass needed)
- A Yellow verdict flips Green after an addendum → move from 🟡 to 🟢
- A build PR ships against a 🟢 (or 🟡/📐) item → remove from this file and let `progress.md` carry it
- **Any ticket that needs Design input gets a row here, in the same breath as opening it** → add it directly to 🕰️ Backlog. Use ⏳ only when the ticket genuinely can't be triaged yet, and move it out in the next edit: ⏳ is an untriaged inbox that `design-status` does not report, so a row parked there is as invisible as no row at all. This is a standing rule (set by Hugh 2026-08-04), and the label is not a substitute: **`design-status` parses this file section by section and never queries GitHub labels at all**, so a perfectly-labelled ticket with no row is invisible to it. It fires most often mid-`epic-run` / `complete-and-ship`, where design questions get spun out as a side effect of building and the tracker edit is the easy step to skip. The row is a repo file, so fold it into the branch already in flight rather than opening a PR just for it. **The label alone is what "getting lost" looks like** — refresh #38 found six such tickets, none of them labelled `type: design`, so no label query could ever have caught them
- **Judge by the fix, not the label.** A ticket needs Design if answering it means deciding a missing affordance, a placement, or a new surface — regardless of whether it was filed as `bug`, `polish` or `feature`. "The plumbing is eng but nobody has decided what it should do" is a design ticket
- A ⏳ ticket gets triaged (state / phase / priority / adjacency checked) → move it to 🕰️ Backlog. ⏳ is an untriaged inbox and is **not** one of the four lists `design-status` reports, so anything left there is invisible in the readout
- A brainstorm starts, pauses, or resumes → 🎨 ↔ 🚦
- **Check the rows you already have, not just the ones you're missing.** Every refresh should confirm each 🟢 / 🟡 / 📐 row's source ticket is still open before trusting it — a closed ticket means the row should have drained to ✅. Refresh #39 found both Greens stale, and a stale Green is worse than a missing row: silence is merely invisible, whereas a Green actively tells an eng-planning agent to go build something that already shipped.
- **Never write a bare "this PR" self-reference in a row — name the PR number.** The phrase is only true while the PR is open; once merged, the file has no memory of which PR carried the edit, so the next reader resolves it to whatever PR they happen to be looking at and the attribution silently points at the wrong work. Copilot caught two such rows on PR #1472, where they credited that PR with a relabel #1468 had actually done. Open the PR first, then write `(PR #NNNN)` into the row — the number exists before the row has to be final. Already-merged ✅ log entries are a frozen record and are not retrofitted; the rule applies to rows being written or edited.
- **Sweep the folders, not just the labels.** A handoff can enter outside Track 2 with no ticket and no brief PR (Hugh authoring an audit directly — see refresh #37), which makes it invisible to both the ⏳ label sweep and the brief-merge trigger above. Any `design-status` refresh should list `design/design_handoff_*/` and confirm every folder appears in a row here or in `progress.md`. A ticketless handoff does **not** need a GitHub issue opened for it — use the `— (no source ticket)` convention at the foot of this file and inline phase/priority in the row's narrative column.

**When NOT to update:**

- Copilot review round churn on any of the above (doesn't change stage)
- Small ops adjustments (branch renames, worktree cleanup)
- Anything already covered by `progress.md`'s substantive-only rule

**PR shape for tracker updates:** doc-only, no Copilot review required. Merge on green CI. Copilot rigor is for briefs / handoffs / audits, not for keeping the tracker in sync with reality.

**Concurrent-edit hygiene:** new entries in the "Recently shipped" table go at the **top** of the table (newest-first, so the most recent context is at eye level). In-flight tables are edited in place when state changes. Rebase-friendly on merge.

**Source ticket references:** every row's **leading column** (whether it's labelled `# / vertical`, `# / handoff`, or `#` depending on the section) should lead with the source GitHub issue number — e.g., `**#72** Shareable show cards ...` — even for pre-existing handoffs. This lets the `design-status` skill fetch phase/priority labels without an extra title-search step. When a handoff has no direct source ticket, note "— (no source ticket)" in the leading column and inline the phase/priority manually in the row's **trailing narrative column** (labelled `Notes` in the 🟢 Ready table, `Blockers to close` in the 🟡 Yellow table, and `Adjacency / notes` in the 🕰️ Backlog table).
