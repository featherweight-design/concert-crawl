## Summary

The handoff is visually thorough — beautiful tier cards, expressive founder urgency, scarcity rail, role-holder voluntary support, payment surface with sheet/modal parity, and a coherent Sour-Patch voice — and the surfaces themselves (tier picker, payment, trial-ended takeover, settings plan card, badges) are buildable from the JSX prototypes. But this is the largest monetization feature in the product's history, and the audit surfaces **six categories of significant gap**: (1) the payment infrastructure assumed throughout the handoff (Stripe Elements, customer portal, webhooks, customer/subscription persistence) does not exist in the codebase yet — the schema has a vestigial 2-tier `subscriptions` table, no Stripe client, no webhook handler, no checkout endpoint; (2) the handoff's 4-tier model (Free / Supporter / Premium / Founder) doesn't align with the shipped 2-tier `subscription_tier` enum (`'free' | 'premium'`) or the 4-state `UserPlan` type (`'founder' | 'paid' | 'trial' | 'past-due'`) — neither the schema nor the type exposes a Supporter tier, a logged-out state, a "free signed-in" state, or the trial→supporter mid-flight tier-switch the design assumes; (3) subscription lifecycle states beyond "first purchase" (renewal, downgrade, cancel, refund, dispute, dunning, win-back, expired-trial-to-free) are explicitly out of scope per the README — but most of them are required before launch, and the design does not enumerate them; (4) fraud / payment-decline / 3DS-challenge / SCA states have no design beyond a single `"error"` state on `PaymentSurface`; (5) tier-feature gating (which tier sees which feature in which surface — Watching, Calendar export, History, Following, Alerts, Spotify sync, Price-drop alerts) is asserted at the tier-card level but not mapped to the actual UI surfaces or to a runtime entitlement check; (6) the design does not cover the Beta-to-Launch spec's "beta preview users get lifetime Premium via Clerk `publicMetadata`" mechanic (specified May 9, 2026), even though the handoff's most recent Round 4 changes (May 18) post-date the spec — so the `'paid-founder'` user state shown in the picker conflicts with both the beta `premium_gifted` mechanic and the eng-side `derivePlan` returning `'founder'` as the *default* for users with no subscription row. Net: a small Design round-trip + a separate eng-led "monetization infrastructure" spec are both prerequisites to opening a plan PR. The visual handoff is not wasted — most of it survives — but it cannot drive a plan PR as-is.

## Per-dimension findings

### 🗺️ Scope clarity

- ✅ Surfaces enumerated explicitly: tier comparison (mobile sheet + desktop matrix), tier-detail sheet, founder urgency variants, founder-window states, payment sheet + modal, trial-ended takeover, settings plan card + role rail, user dropdown, badges. Twelve labeled canvas sections — exhaustive for the surfaces the handoff *does* claim.
- ✅ Explicit "What's intentionally out" section names Stripe Elements internals, artist following UI, notification prefs, and granular admin role assignment.
- 🔴 **Subscription management / cancel flow is also listed as out of scope** (`README.md:113`). That cannot stand for a feature shipping at beta wk 3 — Stripe customer portal alone doesn't cover the in-app downgrade / change-payment-method / "you're about to lose Premium on Aug 12" affordances the handoff implies elsewhere ("Manage subscription" CTA in `Round 4 changes`, "Upgrade or cancel" CTA in `monetization-settings.jsx:348`). The exclusion contradicts the surfaces.
- 🔴 No explicit non-goals around: refunds, disputes/chargebacks, prorated upgrades (Free → Supporter mid-cycle), downgrades (Premium → Supporter mid-cycle), dunning emails, win-back flow, account-deletion-while-subscribed.
- 🟠 No open-questions log at the README level. Eng-side decisions are scattered across "Known visual issue" and inline JSX comments. A consolidated "Open questions" section is the convention every other recent handoff carries (404, price-source, admin-venues #506).
- 🟠 Scope boundary between *tier comparison + payment* (Beta wk 3) and *premium features themselves* (History wk 4, Shareable cards wk 5, Spotify sync wk 7, Alerts launch) is implicit — the Tier card "What's included" lists features that don't exist yet, with no signposting of which are "ship now, gate later" vs. "render placeholder if not yet built". Plan PR needs an explicit per-feature ship state to scope correctly.

### 🎭 State coverage

- ✅ Six user states enumerated and rendered (`logged-out` / `free` / `on-trial` / `paid-supporter` / `paid-premium` / `paid-founder`).
- ✅ Founder-window states enumerated and rendered (`open-many` / `open-few` / `ending-soon` / `closed`).
- ✅ Three urgency intensities (`subtle` / `medium` / `loud`) with Medium as the locked default.
- ✅ Role-holder voluntary support state (Admin / Promoter / Beta with "You're in already" banner, Founder claimable, Free hidden).
- ✅ Trial-ended takeover (day-15) with locked tier order.
- ✅ Mobile + desktop parity is required project-wide (codified in `docs/superpowers/design-pipeline.md` under the State coverage audit dimension); the handoff satisfies it — tier picker (sheet + matrix), payment (sheet + modal), settings (PlanRailMobile + PlanCardDesktop).
- 🔴 **Payment lifecycle states are critically thin.** `PaymentSurface` has `"form" / "loading" / "success" / "error" / "switch"` — five states for the most failure-prone surface in the product. Missing: 3DS / SCA challenge ("redirecting to your bank"), Stripe `requires_action`, decline + specific reason (insufficient funds, fraud block, card not supported, expired, CVV fail), retry / re-enter card, rate-limit / network-loss-mid-submit, customer-already-has-subscription (trying to "upgrade" to the tier they're already on), founder-window-closed-while-checkout-open race, idempotency-failure (double-tap the CTA, server returns the existing sub).
- 🔴 **Subscription-lifecycle states** are not designed beyond first purchase and Past-due. Missing entirely: trial-day-13 nudge ("trial ends tomorrow"), trial-converted-to-paid confirmation, monthly renewal receipt surface (in-app? email? both?), Past-due → Active recovery, Past-due → Cancelled-by-system, user-initiated cancel ("are you sure" flow), cancelled-but-still-active-until-period-end UI, downgrade Premium → Supporter (Stripe prorates — does UI?), upgrade Supporter → Premium mid-cycle, plan-change-takes-effect-at-period-end vs. immediately decision and its UI, account-deletion-while-subscribed (the existing `DELETE /v1/users/me` has no Stripe-cleanup branch).
- 🔴 **Beta preview user state is missing.** Per `2026-05-09-beta-to-launch-design.md:82-88`, 10-20 private beta users receive lifetime Premium via Clerk `publicMetadata.plan = 'premium_gifted'`. The handoff's user-state matrix has no `premium_gifted` mode. The settings plan card surface should not show "Cancel any time" or "Manage subscription" for these users — but the handoff's `PlanCardDesktop` doesn't branch for it.
- 🔴 **`'paid-founder'` collides with `derivePlan('founder')` as default.** Today, `apps/api/src/routes/users.ts:79` returns `'founder'` whenever no subscription row exists (which is *every* user). The handoff's `paid-founder` state assumes Founder = post-launch claimed tier. Reconciling these two meanings of "founder" is design × eng work, not eng-only.
- 🟡 Founder *claimed* vs. *available-to-claim* vs. *closed-but-you-already-claimed* states are present in the tier picker but not in the settings plan card. The "I claimed Founder during the window, now it's closed, here's my permanent $3 price lock" affordance in Settings is undesigned.
- 🟡 No designed behavior for a user whose Founder window closes mid-checkout. Race condition is real.
- 🟡 Logged-out → tier picker → "Sign in to continue" handoff is not designed. The current `monetization-tiers.jsx` `logged-out` state implies the picker is browseable while signed out, but the CTA's destination (Clerk sign-up with tier choice persisted vs. sign-up then re-prompt) is undefined.

### 🔌 Data contract

The state-reachability gate (every named state in the design must be reachable from a real backend) is codified in `docs/superpowers/design-pipeline.md` under the Data contract audit dimension.

- 🔴 **Stripe integration does not exist in the codebase.** No `stripe` package import anywhere in `apps/` or `packages/`. No checkout endpoint, no webhook handler, no customer portal redirect, no `Stripe` client initialization. `STRIPE_SECRET_KEY` is a placeholder in `apps/api/.env.example`. `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` is not present in `apps/web/.env.example` at all. Building any tier-card CTA requires a parallel "monetization infrastructure" eng spec covering: Stripe Customer creation hook (Clerk webhook → create Stripe customer), Stripe Elements client init in Next.js, server-side checkout-session creation endpoint, Stripe webhook handler (subscription.created / updated / deleted, payment_intent.succeeded / failed, customer.subscription.trial_will_end, invoice.payment_failed), customer portal redirect endpoint, idempotency keys for double-submit safety, Stripe Tax considerations (we're not collecting tax today), SCA-region card declines.
- 🔴 **Schema tier enum is wrong.** `packages/db/src/schema/commerce.ts:11-14` defines `subscriptionTierEnum` as `['free', 'premium']` only. The handoff has four tiers. A migration to add `'supporter'` and `'founder'` to the enum is required (expand step), plus a `tier_locked_price_usd` column (Founder's "$3 forever" guarantee can't be enforced if all rows reference a Stripe price that admin can change), plus `trial_ends_at`, plus `cancel_at_period_end: boolean`, plus `founder_claim_order: int` (which Founder slot were you — 1 through 100). **Note on `premium_gifted`:** per `docs/superpowers/specs/2026-05-09-beta-to-launch-design.md:82-88`, gifted beta users are represented via Clerk `publicMetadata.plan = 'premium_gifted'` with **no Stripe subscription row** — and the current schema's `stripeCustomerId` / `stripeSubscriptionId` are `notNull()`, so a gifted column on `subscriptions` would actively contradict the table's invariants. The `derivePlan` rewrite checks Clerk metadata first, then falls through to Stripe — that's where the gifted state lives, not in this table.
- 🔴 **`UserPlan` type doesn't include `free` or `supporter` or `logged-out`.** `packages/types/src/index.ts:590` — `'founder' | 'paid' | 'trial' | 'past-due'`. The handoff's six user states are not representable. Eng cannot wire any tier card to a real prop without expanding this union — and that's a breaking change to the `UserProfileResponse` consumers (`apps/web/src/components/settings/PlanCard.tsx` switches on this).
- 🔴 **`derivePlan` returns `'founder'` for users with no subscription row.** That's wrong for the new model — they should be `'free'`. The current behavior is "Founder = the beta default" (per the type's inline comment). The handoff treats Founder as a paid post-launch tier. These cannot both be true; eng + design need to lock the meaning before the plan PR.
- 🔴 **No billing endpoints exist.** Working assumption for the surfaces this handoff needs: `POST /v1/billing/checkout-session` (Stripe checkout-session create), `POST /v1/billing/portal-session` (Stripe customer-portal redirect URL), `POST /v1/webhooks/stripe` (webhook receiver), `GET /v1/billing/founder-window` (returns seats remaining + close timestamp for the ScarcityRail). **Exact paths to be locked in #775 (the infra spec).** This audit uses these names consistently below as a working contract; if #775 picks different paths, the corresponding plan PR adopts whatever #775 lands. None of the routes in `apps/api/src/routes/` cover billing today.
- 🔴 **`getFounderState()` in `monetization-shared.jsx` is hand-mocked.** The data contract for seats remaining / time remaining is undefined — does eng poll? subscribe via Server-Sent Events? cache for 60s? recompute server-side per request? Without a contract, the ScarcityRail's "9 seats left, closing tonight" countdown can't be shipped.
- 🟡 **Premium-feature gating is unspecified at the type level.** No `entitlements` field on `UserProfileResponse`, no shared helper like `canUseFeature(plan, 'calendar_export')`. Each premium feature (History, Calendar export, Following, Alerts, Spotify sync, Price drop alerts) will need either (a) per-feature plan checks scattered across routes/components, or (b) a centralized entitlements helper. Plan PR has to pick one; design has no opinion. Recommend: centralized helper in `apps/web/src/lib/entitlements.ts` mirrored in `apps/api/src/lib/entitlements.ts`, driven by a single `TIER_FEATURES` map shared via `packages/types`.
- 🟡 **Stripe Price IDs are environment-specific** (test mode vs. live). Plan PR must spec how Price IDs are configured (env vars `STRIPE_PRICE_SUPPORTER`, `STRIPE_PRICE_PREMIUM`, `STRIPE_PRICE_FOUNDER`?) and how they map to tier enum values. No mention in the handoff.
- 🟡 **Webhook idempotency + signature verification** are eng-side but the design has no "we briefly fell out of sync" UI state. Webhooks can lag by seconds-to-minutes. A user who just paid may see "Trial" for 30s after success. Need a "we're confirming your payment" interstitial, or optimistic UI + a "stuck on confirming?" support link if it lingers >60s.

### ♿ Cross-cutting

- 🔴 **No a11y guidance in the handoff README at all.** Tier cards have CTAs — are they `<button>` or `<a>`? The payment sheet is a bottom-sheet modal — what handles focus trap, escape-to-dismiss, scroll lock, `role="dialog"` + `aria-modal`, focus return on close? The `TierComparisonMatrix` is a wide table on desktop — is it a real `<table>` (recommended for screen readers) or divs? Founder scarcity countdown ("9 seats left · closing 11:54 PM") — does it use `aria-live="polite"` so screen readers hear updates? Trial-ended takeover is a full-screen interrupt — what announces it? **Tracked: #771** (Monetization addendum — a11y review pass + screen-reader walkthrough) is the gate that has to close before plan PR can open.
- 🔴 **No analytics / telemetry plan.** Per `2026-05-09-beta-to-launch-design.md` PostHog is the analytics layer. Monetization is the highest-value funnel in the product — every step needs an event (`monetization_picker_opened`, `tier_selected`, `payment_attempted`, `payment_succeeded`, `payment_failed`, `trial_started`, `trial_ended`, `founder_claimed`, `voluntary_support_offered_to_role`, `voluntary_support_accepted`). Plan PR has to design the funnel; design has no opinion. Recommend: PostHog event spec in plan PR with explicit property schemas.
- 🔴 **No legal / compliance guidance.** Stripe is the payment processor (we never see card data), which simplifies PCI compliance — but Concert Crawl is still the merchant of record and is on the hook for required disclosures, receipts, refunds, and tax-policy decisions. Open questions the handoff doesn't answer: do we need a SCA-region disclosure? A "by clicking, you agree to ToS and Privacy" microcopy block above the CTA (Stripe's recommendation)? A receipt-by-email opt-in (not in `apps/web/.env.example`'s Resend setup)? A "subscription auto-renews" disclosure (required in CA, NY, several EU jurisdictions)? Per `2026-05-09-beta-to-launch-design.md:147`, ToS / Privacy / refund policy land in Launch Prep (Aug 4–17) — but Stripe is going live in Beta wk 3 (Jun 30). The legal layer ships *before* the eng layer; that gap is not designed.
- 🔴 **Founder window race semantics.** Per the handoff, "First 100 Founders or 30 days, whichever comes first". With 100 seats and real-time concurrent checkout, server-side seat reservation must be atomic — design / spec for "you started checkout while a seat existed, you're submitting payment now, seat 100 was just claimed by someone else, your card was charged" is missing. Stripe doesn't atomically check seat count; the app does. Plan PR must spec a transactional `SELECT … FOR UPDATE` or Redis lock pattern, AND a UX for "we double-charged you / your spot was taken / here's your refund / you were converted to regular Premium".
- 🟡 **Performance.** Stripe.js is ~70KB gzipped. Loading it on every page that has a "Go Premium" CTA (most pages) will hurt landing-page LCP. Plan PR should defer Stripe.js until the user interacts with a monetization surface.
- 🟡 **Trial-ended takeover is a full-screen interrupt** — it's the single most disruptive UX in the app. No "remind me later" affordance documented; the only options are pick a tier or "Stay on Free". For a user mid-task ("I just opened the app to check tonight's show"), that's hostile. Plan PR or Design should consider a delay-to-next-session pattern.

Plan PR must lock which.
- 🟡 **The handoff doesn't reference the existing `PlanCard.tsx` shipped in PR #49** (`apps/web/src/components/settings/PlanCard.tsx`). Either the handoff was authored before #49 shipped, or design assumed eng would rip-and-replace. Plan PR has to formally document the migration of the existing 4-state copy keys.

## Gaps requiring Design round-trip

The gap bullets below capture what Design needs to deliver. These are **already tracked** by the consolidated addendum tickets at the top of this document (#780–#783) — do **not** open one new ticket per bullet here. The four consolidated briefs each cover multiple bullets; cross-references noted per item.

1. **Subscription lifecycle states.** Cancel-confirmation flow (in-app, "are you sure"), cancelled-but-still-active until period-end card variant, downgrade flow (Premium → Supporter mid-cycle — what does the user see?), upgrade flow (Supporter → Premium mid-cycle — proration explainer copy), trial-day-13 nudge surface (in-app banner or email or both — copy + visuals), past-due → recovered confirmation, past-due → cancelled-by-system final state, account-deletion-while-subscribed warning + Stripe-cleanup affordance. Five-to-eight surfaces. **Tracked in #780.**
2. **Payment failure states.** Beyond `state="error"`, design needs: card declined (with reason-specific copy — insufficient funds, fraud, expired, CVV), 3DS / SCA challenge ("redirecting to your bank, hold on"), Stripe `requires_action` interstitial, retry-with-different-card flow, "you already have this tier" idempotency response. Three-to-five surfaces. **Tracked in #782.**
3. **Beta `premium_gifted` user state.** Plan-card variant for gifted-Premium users (no "Manage subscription" CTA, no "Cancel any time", new copy that thanks them for being in beta), tier-picker handling (offer Founder claim during the window; don't push Premium they already have), settings-page treatment. Two-to-three surfaces. **Tracked in #781.**
4. **Founder availability + claiming.** Does Founder open Beta wk 3, public launch, or somewhere between? If between, what's the "soon" state in the picker? ## Decisions inherited

The plan PR must respect these locked decisions from the handoff README, regardless of how the gaps resolve:

- **Voice = "Sour Patch Kids."** Slight cheek in headlines, gratitude in body. Honesty rail under each tier. Mono eyebrows for meta.
- **Cards carry the personality, not banners.** No giant pricing hero. Free = outlined neutral, Supporter = subtle accent stripe, Premium = signal border + signal CTA, Founder = signal+accent gradient + scarcity rail.
- **Founder countdown = information, not pressure.** Default urgency = Medium (mono eyebrow + thin progress hairline). Loud exists for stress-testing but is not the recommended default.
- **Scarcity = seats + time, both visible.** Mono meta. Loud variant leads with the seats number; Subtle is mono-only.
- **Trial CTA defaults to inline on the Premium card.** Banner placement is opt-in via Tweaks (i.e. not the default ship).
- **Role-holders see the same picker** with the "You're in already" banner, Founder claimable, Free hidden, Supporter recoloured as voluntary. Headline shifts to "Wanna chip in?".
- **Payment surface wraps Stripe Elements.** Trial path shows `$0.00 due today` + `$5.00 in 14 days`. Founder shows scarcity rail at top of the payment surface.
- **Token-only colors.** Every accent reads from `var(--signal)` / `var(--accent)`. Cross-theme parity required (and must extend to the 6 newer themes per drift note).
- **Tier copy table** (Free / Supporter / Premium / Founder taglines + rationales + CTAs) is locked.
- **Success-state headlines** are locked (Trial: "Trial's running."; Founder: "Founder. Locked in."; Supporter: "You're a Supporter."; Premium paid: "You're in.").
- **Tier badges** (cosmetic chips) + **Role badges** (utility chips) compose via `<BadgeRow tier role/>` in 3 sizes (sm / md / lg). Both are part of the ship.
- **Tier details modal** (`<TierDetailSheet/>`) opens from each card's "See what's included" button.
- **Current-plan stamp** (✓ YOUR PLAN banner + 2px accent border + neutral "Manage subscription" CTA) on whichever tier the user is currently on.
- **Trial-ended emphasis:** Founder is the only glowing CTA; Supporter and Premium share the secondary treatment even when Founder is closed.
